# MCP grant grammar — do server-level patterns in `tools:` resolve?

    Harness:   Claude Code 2.1.220
    Date:      2026-07-29
    Fact:      platform.md fact 13 (and a correction to a recommendation in verification.md)
    Fixtures:  .claude/agents/wf-mcp-{wildcard,bare,exact,search}-probe.md
    Spawned:   all four from the main conversation (depth 1), foreground, one message
    Server:    playwright-mcp — 32 tools, the instrument rather than the subject

## Why this design

Four grants, one variable each, one shared return grammar so they tabulate. Each fixture attempts one
real call (`suite_methodology({topic:"overview"})` — a file read inside the server, no browser, no
network) because a visible tool name is not a callable one.

## Verbatim returns

```
MCP_GRANT_PROBE | FIXTURE: wildcard | MCP_NAMES: 32 | DEFERRED: no  | TOOLSEARCH: no  | CALL: ok
  TOOLS: Read, mcp__playwright-mcp__browser_click … web_fetch    (32 server tools, full list in transcript)

MCP_GRANT_PROBE | FIXTURE: bare     | MCP_NAMES: 32 | DEFERRED: no  | TOOLSEARCH: no  | CALL: ok
  TOOLS: Read, mcp__playwright-mcp__browser_click … web_fetch    (identical 32)

MCP_GRANT_PROBE | FIXTURE: exact    | MCP_NAMES: 1  | DEFERRED: no  | TOOLSEARCH: no  | CALL: ok
  TOOLS: Read, mcp__playwright-mcp__suite_methodology

MCP_GRANT_PROBE | FIXTURE: search   | MCP_NAMES: 32 | DEFERRED: yes | TOOLSEARCH: yes | CALL: ok
  LOAD_REQUIRED: yes | UNGRANTED_SERVER_SCHEMA: withheld
  TOOLS: Read, ToolSearch, mcp__playwright-mcp__browser_click … web_fetch
```

## Results

| # | Grant | Result |
|---|---|---|
| 1 | `mcp__playwright-mcp__*` | **resolves** — all 32 tools, **loaded**, directly callable |
| 2 | `mcp__playwright-mcp` | **resolves identically** — the suffixless form is not a different thing |
| 3 | `mcp__playwright-mcp__suite_methodology` | **exactly one tool.** Naming one does not deliver its neighbours |
| 4 | `mcp__playwright-mcp__*` **+ `ToolSearch`** | resolves, but **deferred**: a load step was required before the call |

**Fact 13 is confirmed and promoted to MEASURED.** Both server-level forms resolve, and the names
arrive loaded. The web-facing handbook grant that ships in `handbook-templates.md` works on this host.

## The finding nobody was looking for

**Adding `ToolSearch` to the grant made the MCP tools deferred.** Fixtures 1 and 2 — same session, same
server, same 32 tools, no `ToolSearch` — reported `DEFERRED: no` and called straight through. Fixture 4
differs by one granted tool and reported `DEFERRED: yes, LOAD_REQUIRED: yes`.

So `ToolSearch` is not a free hedge against a grant that might not resolve. **It makes the grant lazier,
not safer:** it inserts a load step in front of tools that were directly callable without it. A
recommendation to add it "just in case" was written into `verification.md` earlier the same day, on the
assumption that it could only help. It is retracted here.

Stated honestly: one run per fixture, and the deferral could in principle be a context-size effect
(MCP tool descriptions auto-defer above a share of the context window) rather than caused by the grant.
The A/B is clean as far as it goes — same session, one line of difference — but it is a single pair.

## The ceiling holds

`UNGRANTED_SERVER_SCHEMA: withheld`. Fixture 4 held `ToolSearch` and used it to look for
`mcp__nanobanana-mcp__set_model`, a tool from a server its `tools:` line never named. The schema did
not come back.

**So `tools:` is a real ceiling for MCP reach, not merely a default** — granting `ToolSearch` does not
open a side door to unnamed servers. This is a *prevents*, and it is measured; `enforcement.md` carries
it as one.

## Consequences

1. **Grant MCP servers at server level** — measured to work, and it survives tool renames between
   releases.
2. **Never add `ToolSearch` alongside an MCP grant** to hedge. It costs a load step and buys nothing.
3. **Enumerating tool names is exact** — correct, but no safer than the pattern, and it breaks when the
   server renames a tool.
4. **A grant naming a server the host has not configured is still untested.** Every fixture here ran
   against a server that exists. What an employee sees when the server is absent is the open question
   that matters for anyone else running this project — see `verification.md` § When the server is absent.

## Fixture disposition

Retained, not deleted. `staging.md` § Fixture lifecycle permits deletion after a recorded run; these are
the instrument for re-measuring the grant grammar after a harness upgrade, and re-measurement is a
standing obligation (`README.md` § Re-measuring). They cost four lines in a session's agent listing.
