The list was written by the head that was tunneling (v1.42.0)

ASKED FOR by the user, three questions in one: has the defect been corrected, is
there a mechanism that fires on the NEXT dev session to catch half-finished work, and
does workforce dev run what it ships to others. Enumerated rather than recalled — the
ask tagged `existence`, and a sample cannot show what is absent.

THE ANSWERS WERE NO, NO, AND HALF.

NO, THE ROOT DEFECT WAS NOT CORRECTED. v1.41.0 added a check for one TRACE of a
missing component — a hand-off file written and never read. The defect itself is that
"done" is defined by a list the operator writes, and nothing compared stated work
against delivered work. MEASURED: a goal held its condition, four suites went green,
and the work was half done, because the list omitted the acting half of the mechanism
being built. Checking that list is the tunnel grading its own homework against an
answer key it wrote.

NO SESSION-START MECHANISM EXISTED. This distribution shipped hooks for exactly four
events — PostToolUse, Stop, SubagentStop, UserPromptSubmit. Nothing fired when a
session began, so nothing could carry an unfinished thing across the boundary where
it matters most.

AND THE ENFORCEMENT WAS IN THE ONE PLACE THAT DOES NOT SHIP. The
detector-ships-with-its-actor rule went into `bin/check`, which is maintainer-only and
in no manifest. Every host carried the directive it enforces — "A DETECTOR SHIPS WITH
ITS FIX", SKILL.md § Directives, 2026-08-05 — and nothing on any host could check it.
Now in `wf-live`, which ships, so a host gets it from `verify` and from a bare run.
The hooks themselves were already fine: all registrations are user-scope, so the dev
kit runs exactly what it installs elsewhere.

`wf-commitments` IS THE MECHANISM, ON BOTH ENDS OF A SESSION. At `Stop` it records
what the turn said it would do NEXT; at `SessionStart` it reads the ledger back before
the first request. Per-PROJECT, not per-session — a session-scoped file would clear
exactly when a new session made it matter.

WHAT IT CAN AND CANNOT DO, stated because the limit is the honest part. Nothing on
this machine knows whether the RIGHT list was written; that is the defect and it is
not mechanisable. What is mechanisable is narrower and still worth having: **a list
stated out loud is a debt, and a debt must not evaporate silently.** It cannot make a
list complete. It stops an incomplete one from being quietly forgotten, which is the
failure that actually happened.

It is SKILL.md's deferment-queue directive pointed at the operator — "all items in the
deferment queue should be resolved one by one ... NO EXCEPTIONS! NO BLOCKS! NO
EXCUSES!" was written about a run's deferred findings; this is the same rule applied
to the one queue nobody was keeping.

IT NEVER JUDGES WHETHER AN ITEM IS DONE. A regex making that call would close debts
that are still open, and an item wrongly closed is invisible while an item wrongly
kept is one line a reader dismisses. Past tense is excluded on purpose: "I wired the
manifest" is a report, "I'll wire the manifest" is a debt, and only the second can go
unpaid. Fixture `commitments-ignores-a-report` holds that line.

ONE FALSE POSITIVE INTRODUCED AND CLOSED IN THE SAME PASS. Teaching `wf-live` the
detector rule made it report `wf-widen-agent` as a phantom — a `type: "agent"` hook is
a prompt, not a file, so "is there a file behind this name" is the wrong question for
it. Correct-looking false positives are what teach a reader to skim a report, which is
what a 7.0% guard was retired for here.
