The reply half of asks: N — counted for free, judged where judgment belongs

`wf-task-tag` counts how many things a message asked for. On its own that is a
flag, and a flag is not a fix. This is the reply half, and the user asked the
right question about where it goes: "there is that stop where the reply gets
graded by the senses — could it be embedded there?"

BOTH, because they are two different questions, and `wf-widen`'s own docstring
already states the rule: "Cheap decides, expensive acts."

COUNTING SECTIONS IS A REGEX AND FREE, so it runs on every multi-ask turn, in
`wf-commitments`. Spending a subagent to count `##` is the waste the user's
second directive names — "if that data answers the users question directly why
spin it up in agent use all those tokens." And the jury fires on ~10% of turns
by design, while a reply-shape line should see all of them.

IT LIVES IN wf-commitments AND NOT IN wf-widen FOR ONE MEASURED REASON:
`wf-widen-agent` blocks, and hours earlier today it held three consecutive turns
on one stale conclusion. `wf-commitments` has never blocked anything — no
`return 2`, no block decision — and it already reads the reply and already
surfaces what it finds. A reply-shape observation is worth a sentence, never a
held session.

WHETHER SECTION 2 ANSWERED ASK 2 IS A READER'S JUDGMENT, so `asks` and
`asks_why` now ride the widen flag. That question was unaskable before: the flag
carried `ask.prompt` as one undifferentiated string, so the jury could see WHAT
kind of question was asked and never HOW MANY things were in it.

MAX, NEVER SUM, across the three section families. A reply that numbers its
sections and bolds their labels is the ordinary way to write one, and summing
inflates the count so the check passes on exactly the replies it exists to catch.

And it is silent when there is no tag. None is not 1: a turn nobody classified
was never counted, and asserting a shape against a count nobody took is the
vacuous pass this project refuses everywhere.

FOUND BY RUNNING IT, not by reading it. The first version sat AFTER
`if not fresh: return 0`, so it fired only on turns that also stated a
commitment — and a turn that blends three answers into one reply promises
nothing, so the population it was written for was precisely the population it
could not see. A 3-ask prompt against a 1-section reply printed nothing at all.
Parse passed; the branch was dead. The assertion now pins the ordering.

Measured on four payloads: 3 asks / 0 sections warns; 3 asks / 3 headings silent;
3 asks / numbered-and-bolded silent rather than inflated to 6; no tag silent.

Three asks came back as one answer, because nothing counted them

The user sent three numbered issues in one message and had to ask whether they
were the cause of the confusion: "if I'm confusing you and causing you to mix up
the different issues, let me know that too." They were not.

`wf-task-tag.classify` already returned an ARRAY, and deliberately — its own
comment: "NOT first-match. An ask can be two kinds at once." But the widen flag
carries `ask.prompt` as ONE undifferentiated string, so the dissection ran along
the epistemic axis (what KIND of question) and never along the cardinal one (how
MANY things were asked). Enumerated both hooks before claiming the gap: nothing
counted distinct requests anywhere.

DETECTOR. `count_asks` returns (n, why) — the count and the evidence for it,
because a bare number gives a reader nothing to check and this one decides how a
reply is shaped. `asks` and `asks_why` now ride both tag writes.

EXPLICIT ENUMERATION ONLY, and the restraint is the design. Segmenting free prose
into distinct requests is judgment; a regex guessing at it reports 3 on one long
sentence and 1 on three short ones, and a number wrong in both directions is
worse than no number because the reply gets sectioned against it. A count the
user STATES is authority and is read literally, bounded 2..9 so "a hundred things
wrong with this" stays exasperation rather than becoming a docket. An ordinal with
no stated count returns 2 and says it is a FLOOR.

Measured on seven prompts including the real message that prompted this: 3 from
"there's three things here", 2 from "two issues", 3 from a numbered list, 2 from
an ordinal-only floor, and 1 from each of a single ask, a bare question, and the
exasperation case.

FIX, because a counter that changes nothing about the reply is a flag and a flag
is not a fix (§ Directives, 2026-08-05). Operating-principles item 14: one
heading per thing asked, in the order raised, each answered or explicitly named
as not answered. It sits INSIDE the `WF-PRINCIPLES` region, so `wf-companion`
heals it into orgs that already exist instead of reaching new installs only.

Also in this commit, and it is a correction of work from an hour earlier: the

Direction attached to an audit now survives every hop

The user asked for additional parameters on `/workforce audit` that are followed
throughout the whole run. They were already writing them — "focus on the plugin
and the logs", "don't run the e2e suite or touch the database" — and nothing
received them.

`procedures/intent-router.md` states it plainly: "Arguments are never interpreted
here. Flags, modes, and dates go through verbatim." No gate downstream received
them either, so the words landed in the run's own context as ambient instruction,
reached no sub-process, and were resolved by judgment with nothing carrying them
anywhere. Two MEASURED costs on one machine on one day:

  · An audit invoked from the user's home with a focus on two directories CREATED
    `~/verify-leads-ops` — a directory holding nothing but `.claude` — and wrote
    the whole company into it. Neither focus directory was inside it. The org was
    correct, complete, and reachable from nowhere the user works.
  · An audit ran that project's e2e suite and wrote junk rows into a live
    database.

Step 0.01 — the RUN ORDER. Runs before every other gate, nothing writes until it
has printed. Four fields to `${run-dir}/RUN-ORDER.md`, on disk because shell
state does not survive: REQUEST (verbatim), Constraints, Root, Subject. Echoed to
the user before the first write — a run that resolved the wrong root has spent
the whole session before they can see it, and the root is one line.

THE ROOT IS RESOLVED ONCE AND NEVER INVENTED. Every shipped block spells it
`${CLAUDE_PROJECT_DIR:-$PWD}` — 35 call sites across 9 files — the variable is
measured unset in the Bash tool, and the Bash tool's cwd is harness state that
may persist or reset. Each site was a separate process asking where it was and
getting an answer nobody in the procedure owned. And the root must ALREADY EXIST:
nothing in the distribution sanctions creating one, `scopes.md` says the opposite,
and Core Principle 5 forbids inventing exactly this.

CONSTRAINTS ARE FORWARDED. Not merely honored at the top — carried verbatim into
every dispatch, which is the `REQUEST (verbatim)` rule the dispatch CHECKPOINT
already imposes on every work order an org issues, applied to the audit's own
invocation.

The probe is the hop that needed it and the hop that refused it. Its dispatch said
"This dispatch carries no `REQUEST (verbatim):` block, and that is by design", and
its executor is spawned `tools: Read, Write, Bash` and told to follow the handbook
EXACTLY — so a handbook whose `## Verification` names an e2e target is an
instruction to run it, against whatever database that target writes. The gate
fires before every registration and after every amendment: per employee, per
edit, not occasional. `verification.md` already held the rule that the RUNS and
DISCRIMINATES tiers are run BY HAND and that no shipped tool executes them. An
agent with a shell is not a shipped tool, and nobody had counted it.

The probe now carries the Constraints block, is told it is proving the handbook
FOLLOWABLE rather than the project WORKING, is refused the named side-effect
families even when the handbook it is obeying names one, and returns
`FAIL: probe task requires a side effect` rather than proceeding.

A constraint the run cannot honor is reported in one line, never dropped, and
everything it does not block still finishes.

4 assertions, 4 prove cases, each PROVEN by deleting the guard it names.

The guard was in bullet 1 and the imperative was in bullet 2

MEASURED 2026-09-11, reported by the user against their live WordPress site: an
audit ran the project's e2e target and wrote junk rows into the production
database. Not hypothetical and not a subagent — the audit itself.

`procedures/org.md` § Mode: index said both things, four lines apart:

  1. Find the command's discovery mode ... **It must execute nothing.** A mode
     that runs, writes, or deploys is not a discovery mode, and calling one here
     would make `index` a destructive command.
  2. **Run it** and derive `Covers` from the output ...

The antecedent of "it" is the discovery mode. The constraint that makes that safe
lives in the bullet above, and the only line carrying a verb is bullet 2. To a
cold reader deep in a run, against a `scripts` key holding `test:e2e`, "Run it"
is an instruction to run the command. Four lines apart is not the same file.

Two lines up, "Verify each command resolves before writing its row" named NO
method. Running a command is the most obvious way to learn whether it resolves,
and that sentence had stood with no method since it was written.

Fixed in the wording, which is the whole guard here: `index` is documented
low-risk and executes immediately, so nothing gates it in front and no deny rule
stands behind it.

- Bullet 2 is now "Run THE DISCOVERY MODE — never the command itself", with the
  STOP inline rather than inherited: an invocation that would execute the target,
  migrate, deploy, seed or touch a database is not a discovery mode, and bullet 4
  (`Scope: declared`, one extra hop, capability kept) is the correct outcome. The
  destructive families are named literally — e2e and integration targets,
  db/migrate/seed/fixture, `wp db`, `drush`, `rails db:*`, `artisan migrate` —
  because "not a discovery mode" is a classification a run has to make and `wp db`
  is the one it got wrong.
- Resolution now names a non-executing method: `command -v`, the script on disk,
  or the declaring `scripts` key.

STILL OPEN, and stated rather than implied: this is prose, and prose is what just
failed. The mechanism workforce already owns is `permissions.deny` with the
`.settings-owned.json` sidecar — reversible and recorded. An audit should install
deny rules for the destructive commands its own census FOUND, at Step 0, and
remove them at close. Deriving that set from the project rather than shipping a
guessed list is the recruiter-research pattern, and it is not built.

The loop stop was on the two hooks that cannot block, and not on the one that can

MEASURED 2026-09-11, in this session: three consecutive Stop blocks, each
re-judging ONE stale conclusion through two explicit corrections of it. The juror
never saw the corrections.

`stop_hook_active` is true on the second and later Stop firings of a single turn,
and returning early on it is what stops a Stop hook blocking forever.
`wf-widen` carries that guard at line 485 with a comment naming the exact
failure — "without this a widen that keeps scoring low blocks forever and the
session is dead" — and `wf-turn-ledger` carries it at line 400. Both are command
hooks and neither can hold a session.

`wf-widen-agent` is the one whose `ok: false` actually blocks, and it had no
guard: `stop_hook_active` appeared nowhere in its prompt and nothing else
gated it. The flag it reads is cleared by `wf-task-tag` at `UserPromptSubmit`,
and a Stop-block continuation is a system injection that never fires that event
— so the flag survives holding the original turn's conclusion, the agent
re-reads it, and votes the same verdict again. Unbounded until the user types
something.

An autonomous `audit` is the worst case for it: one `UserPromptSubmit` when the
user invokes the command and none for the next hour, so nothing clears the flag
for the remainder of the run, and `wf-widen` is on `SubagentStop` too.

Diagnosed wrong twice before it landed here, both times by concluding absence
from a search that could not have found the thing. First claim: nothing clears
the flag — false, `wf-task-tag:228-239` does, at the head of every turn. Second:
no cap on consecutive blocks exists — false, two of the three hooks have one. The
grep behind that searched `block_count|consecutive|once per` and never
`stop_hook_active`. Core Principle 5 is "absence is not a gap"; a failed grep is
not a measurement, and an outside reader caught both.
