Carried rows a session drops come back, and a late close in an older list reaches the ledger

Reported from tmux-revive (session ca202cd9) the turn after 1.85.0 shipped. The new STILL OPEN list showed finished work as open: i31, i33, and parts of i26 and i35. Two session habits caused it, and models will keep both:
- The session rewrote each new wf-asks file from scratch with "carried": [], discarding the rows the hook had pre-filled, so nothing closed them.
- It set "done" in the OLDER per-message files, which the ledger never reads again after that turn's Stop.

restore_carried (wf-task-tag, run from the PostToolUse display) re-adds the missing carried rows from carry_forward(ledger), only for issues older than the list's own, and says so in one line while the session can still use them. Rows the session kept are untouched. An emptied list still closes nothing, because absorb_carried writes only rows that exist.

late_marks (called at the main Stop in wf-widen, after absorb_items and before judge_ledger) reads up to 32 of the session's own list files and applies forward moves only: open in the ledger, finished in a file. It never appends an item, never writes to a closed issue, and routes each item the way absorb_items would, so an item on a merged issue lands on its successor. absorb_carried now refuses to move a finished item back to unfinished, so a restored or stale "open" row cannot reopen anything.

Security review: late_marks is the first reader here to take names from a directory listing, and that directory can fall back to /tmp. read_json_nofollow cannot refuse a FIFO, because os.open blocks first, so another account's FIFO under a matching name would hang every Stop. Each entry is now checked with scandir first: a regular file, not a link, and owned by this account. With a planted FIFO the fixed code gives rc=0; without the check it gives rc=124 (killed by timeout).

Code review: no HIGH. The late_marks and absorb_carried match loops are left as two copies on purpose, below the rule of three, because their callers and guards differ.

bin/script-conformance 719 -> 722 of 722. Each new fixture fails against its planted defect. The engineering-coder Negative exits 1 as required.
