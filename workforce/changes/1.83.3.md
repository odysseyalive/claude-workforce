Two downstream complaints: the code map is not a dead Sources channel, and the artifact rail lights the right section

1. wf-conform. 1.78.0's handbook template puts `Skill(records-code-map)` in
every IC's `## Sources` with no `## Procedure` step, and wf-conform's
access-channel row flagged exactly that shape as a dead pointer: 18
advisories on one real org on 1.83.2, all of them the template applied
faithfully. The code map is how the Sources section's own "search every
source above" is carried out, not a store of the role's truth, which is what
the access-channel rule exists for. So the checker exempts that one name
(NAVIGATION_SOURCE_SKILLS) and every other `Skill(X)` stays bound. Fixed in
the checker, not by adding a step to every handbook, so existing orgs heal on
`update` with no re-audit. org-design.md § The access channel and
handbook.md state the exception. Proof: that org went 18 -> 0 code-map rows
(84 -> 66 advisory). Fixture conform-sources-code-map-exempt fails with the
exemption removed and fails with it widened to every skill.

2. shared-artifact template. A clicked contents-rail entry often lit the
section before it. The rail script was an IntersectionObserver band
(rootMargin -20% 0px -70% 0px); a clicked link scrolls its target above the
band, so the previous entry stayed lit. Replaced with a scroll-position
script: the last section whose top has passed 30% of the window, the last
section at the page bottom, and a clicked entry held 1.2 s while the page
scrolls. house-style.md describes that method. Proof, Playwright at
1280x800: all 5 rail clicks light the clicked entry; top and bottom of the
page light the first and last.

Task tag: the checklist display says the partition line for one message's many asks

89c606c says PARTITION_LINE at submit once three items are carried. That
missed the measured i1 in runpod-claude-gateway 89bbc493: ONE message with
16 asks, nothing carried at its submit, so the count was zero and the asks
were worked one at a time. The submit cannot see a message's own asks; they
are not written yet.

The PostToolUse checklist display (_show_checklist) is the first moment
they are on disk, and it fires before the work. When the written list's
open items plus its carried open rows reach PARTITION_MIN, the display now
leads with PARTITION_LINE, ahead of SHOW_LIST and the list. Same constant,
same threshold, no second copy of the wording.

Once per message, never twice in a turn:
- the submit marks its record `partition` when it said the line, and the
  display skips a list whose record carries it;
- the display remembers each list it led with under PARTITION_SAID in the
  existing shown memo, pruned to the lists the tag still carries, so a list
  re-shown after a status change is not led with it again. A non-string
  entry in that memo is ignored rather than trusted.

SHOW_LIST moved from checklist_display into _show_checklist, so the helper
returns the whole display; the output is unchanged when the line is not said.

Demonstration: a throwaway project, a 3-ask message submitted with nothing
carried, the list written, the PostToolUse display piped to wf-turn-budget.
The fixed hook's additionalContext opens "With this many items open they
are partitioned ..." then "Show the user this work list now". A copy with
the lead planted as "" shows only the list.

Fixtures: partition-display-below-threshold (2 asks, absent),
partition-display-at-threshold (3 asks, nothing carried, present and ahead
of SHOW_LIST), partition-display-counts-carried-rows (1 ask + 2 open carried
+ 1 done carried, present), partition-display-said-once-per-list (re-shown
list, absent), partition-display-submit-already-said (submit said it,
absent). On 89c606c's hook 3 of 5 fail; the two absence cases pass there and
each fails when its own guard is removed. bin/script-conformance: 705
passed, 0 failed.

Task tag: several open items are partitioned across subagents, not queued

In runpod-claude-gateway (session 89bbc493, 2026-11-02) the user sent about
twelve asks while a turn ran, touching disjoint files, and the session worked
them one at a time in the main thread: i1..i10 hold agents: 0, only i11 has
agents, opened by the user asking why the items were being stacked instead of
sectioned off to agents. That project has no org chart, so DISPATCH_LINE was
never said, and CARRIED_LINE asks only that statuses be updated. Nothing in
the UserPromptSubmit context spoke to the backlog.

wf-task-tag now says one advisory sentence, PARTITION_LINE, once a turn
carries PARTITION_MIN = 3 or more open items. It is built in earlier_lines, so
it reaches both checklist variants: a message that opens an issue, and the
carry-only turn (an injected hand-back or notice), which is the turn on which
the session is free again with the backlog still open. It is said with or
without an org; where there is one, DISPATCH_LINE still names the employee.
Its last clause keeps an item an agent already holds with that agent, so a
hand-back turn is not told to re-dispatch in-flight work. No gate, no Stop
check.

Not built: a Stop-time check flagging a turn that closed N items serially
with no Agent call. It would be a detector without a fix and an activity
tally.

Demonstration: a throwaway project holding three open items on i1, a new
message piped to UserPromptSubmit. The fixed hook says the carried line and
then "With this many items open they are partitioned rather than worked one
after another: ...". The same run against a copy with `>=` planted as `>`
says the carried line and no partition sentence.

Fixtures: partition-line-below-threshold (2 carried, absent),
partition-line-at-threshold-no-org (3 carried, no org, present verbatim, no
dispatch line), partition-line-with-org (both lines), partition-line-handback-turn
(carry-only turn, present). On the old hook 3 of the 4 fail and the
below-threshold case passes. bin/script-conformance: 700 passed, 0 failed.
