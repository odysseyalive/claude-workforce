version discipline: a shipped change must advance WORKFORCE-VERSION, enforced

`workforce update` is fully scripted — it re-runs the published installer with the
scope forced — so a past run that "changed the version" was the model editing the
anchor by hand, in the wrong place. The number belongs where a change is MADE, and it
was riding unbumped: 1.0.0 through every recent commit while fixes landed in bin/ and
references/, so `update` reported 1.0.0 -> 1.0.0 over a changed tree. That is the
"version blindness" this removes.

- WORKFORCE-VERSION (references/version.md) is the sole authored anchor; SKILL.md's
  required frontmatter `version:` is a checked mirror, asserted byte-equal by bin/check
  and proven by a bin/prove del-case on the `WORKFORCE-VERSION:` key (carries no number,
  so it survives every bump). Bumped 1.0.0 -> 1.1.0.
- bin/pre-commit-version (maintainer-only, NOT shipped) refuses a commit that touches a
  shipped file without advancing the number, a mirror left behind, or a backward move.
  Wired via core.hooksPath -> githooks/ by bin/dev-hooks-install; proven by
  bin/pre-commit-version-test (five scenarios).
- install/install.ps1 echo WORKFORCE-VERSION per scope, and the downgrade guard moved
  from update's procedure into the shared installer (new --force / WORKFORCE_FORCE), so
  a bare ./install and /workforce update protect and report the same number.

Prompted by a maintainer asking whether `update` is AI-driven or scripted; the fixes
that reached a live project came from its personal install being refreshed to HEAD,
not from update-vs-install differing (they are the same code path).

code-eval: add a language-agnostic resource-awareness dimension (RC1-RC6)

The code catalog reviewed structural quality (dead code, duplication,
complexity, minimalism) but had no resource-behaviour axis: `memory`/`CPU`/
`allocation`/`leak` appeared zero times, and `performance` appeared once, only
to defer it to "other passes" that never existed. The complexity pass scores
cyclomatic/cognitive complexity (a maintainability proxy), not computational
time/space cost. This fills that gap.

Online research into expert practice across four unrelated memory models --
C++ value semantics, Python names-bind-objects, PHP zval/copy-on-write,
JavaScript reference-vs-primitive -- collapsed onto ONE set of six cost classes:
RC1 needless copy/value-vs-reference, RC2 materialize-instead-of-stream,
RC3 unbounded retention (leak), RC4 allocation churn on a hot path, RC5 wrong
container/representation, RC6 type/shape stability in hot code. The convergence
across four runtimes is the grounding, so the taxonomy and its detection
heuristics are agnostic and the per-language table is only an illustrative
surface; RC6's engine specifics are demoted to that appendix.

Three disciplines borrowed from the catalog's existing epistemics keep it safe:
every finding is report-only (a candidate, not a verdict -- no static reader
sees runtime scale), fires only through the scale gate (a hot path + file:line
or it is not reported; RC3 leaks excepted), and a resource safety floor makes
premature/ineffective optimisation itself a false positive. Cited-not-measured,
four primary sources per class.

Lands in the authored slot (vendored corpus untouched) at code-additions-version
3, with a bin/check coupling assertion (signals inseparable from report-only +
the scale gate) and a bin/prove del-case that flips it. Re-seeded into this
repo's own catalog via wf-seed (v2->v3). A cold-read Off-the-Street probe read
only the installed section and applied it to a known-answer diff -- flagged
every real hot-path cost, withheld both planted false positives, no AMBIGUOUS.

Drift has a direction, and sync refuses to destroy work

`bin/check` reported a personal-install file as "drifted" and could not say which
side was newer, so the row read IDENTICALLY whether `bin/sync --personal` was
about to deploy a fix or delete one — and it named that command as the fix either
way. `bin/sync` is delete-then-rebuild, so in the second case its advice WAS the
destruction.

MEASURED 2026-08-10: `references/procedures/intent-router.md` was edited in the
personal install, never promoted to source, and was newer there. The row said
"2 drifted" and recommended the sync. It survived only because a human diffed the
file by hand while doing something else, with no reason to beyond suspicion. The
docstring already said "never edit the runtime copy" — a directive, with no
mechanism behind it.

bin/sync now REFUSES while any target file is newer than its source, lists each
with its source path, and names the remedy: promote, then re-run. `--force`
discards them and says so per file. The manifest parse moved ahead of the rmtree,
because the scan has to read the copies the script is about to delete; the flag
and on-disk handling it used to do inline now has one home in manifest_entries().

bin/check splits the two directions. `N stale` keeps the sync remedy; RUNTIME-FIRST
gets a row of its own so it cannot be read as a footnote to the staleness one.

mtime is the signal and it is sound here: shutil.copy2 preserves it, so a fresh
copy and its source share a timestamp exactly, and "newer" means "written after
the last sync". Equal mtimes with differing content are reported UNDATED rather
than ordered by a guess.

Proven by breaking, both halves:

- bin/sync: a runtime-first edit refuses at exit 2 with the edit intact; --force
  discards it loudly; a clean tree proceeds at exit 0.
- bin/check: deleting only the ternary that classifies direction — leaving every
  message string intact — sends both directions back into _drift, and the
  runtime-first row goes SILENT on a real runtime-first edit. The first draft of
  the guard PASSED that revert, so it now asserts the ternary itself. The vacuity
  was found by running the revert, not by reasoning about it.

Reviewed under /code-evaluator review before commit (the project's commit gate).
Two findings in the new code, both applied: unclosed file handles in the scan,
and mtime locals named `d`/`s_` where the surrounding scope already binds `s`.

A preserved annotation is preserved whole

`wf-ratchet --capture` split a baseline row on every `|`, escaped or not, so a
`why` citing `<!-- origin: user \| immutable: true -->` was rewritten to
everything left of the first pipe. Measured on apps-odyssey-alive: 634 characters
to 114, silently, exit 0, dropping both rules the cell cited.

`\|` is markdown's escape for a literal pipe, and the two columns the baseline
header INVITES a human to hand-edit are prose — a rule quoted from a marker, a
table, an alternation. So the restriction was unstated and violating it was data
loss with no error, in the one column that records why a finding was ACCEPTED.

Reader and writer are one pair: reading unescapes, writing escapes, so a value
round-trips unchanged through any number of captures. Fixing only the reader
would parse a cell in and corrupt it on the way back out.
