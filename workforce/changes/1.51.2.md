Four citations were reported missing while both files were on disk

`wf-live` reads a backticked `references/<x>.md` as a citation of OUR tree.
The leading-boundary rule added in 1.48.0 closed the shape that carries its own
root — `skills/text-eval/references/ai-patterns.md` — and cannot see the shape
where ownership is in the prose and the path is bare: "the evaluator skill's own
`references/additions.md`" is relative to THAT skill.

MEASURED 2026-09-11: four such citations (evaluators.md:526, :536, :658 and
procedures/audit.md:1799) sat in the disagreement list while
skills/text-eval/references/additions.md and
skills/code-evaluator/references/additions.md were both present. 26
disagreements, 4 of them phantom, in the tier that exists to be signal.

SKILL_OWNED requires BOTH conditions, so the phrase cannot become a way to
silence a real defect: the sentence must attribute the file to a skill, AND the
file must resolve under one of the shipped skills. Prose attributing a file
nobody has still reports.

GUARDED BEHAVIOURALLY, for the reason the wf-seed block already states — every
source assertion would also pass on a comment. The check copies the tree, plants
three shapes, and runs the shipped CLI: an unattributed citation of a missing
file must report, `skill's own` pointing at a file no skill has must report, and
an attribution that resolves must not. Proven by breaking: neutering the rule
fires "the false positive is back".

26 disagreements -> 22. The BROKEN tier is untouched and still fires on
`Run \`references/gone-imperative.md\``.
