Fix four defects from nc-audit's 1.64.0 re-test, three wider than reported

1. `allowed-tools:` IS NOT A KEY THE HARNESS READS, and the consequence was the
opposite of a tight ceiling. `character-scanner` and `image-validator` declared
it, so each install registered an agent that received EVERY tool while its
frontmatter read like an allowlist. Confirmed from the host's own agent listing,
which renders both as "Tools: All tools" beside the two `tools:` siblings
printing their real grant. A package defect, not audit work: the manifest ships
both AGENT.md files and `agent` rows register them, so every install re-created
it and a local edit would be overwritten by the next `update`.

NOT converted literally to `tools: Read, Grep`, which is the fix that looks
right and ships a lie. `Grep`, `Glob` and `WebFetch` are absent from this host's
registry (measured 2026-09-10 on 2.1.266; platform.md line 333 — "never assume
`Grep` or `Glob`, ground file-finding steps in `Bash`"), and fact 13b says an
unresolvable name in a `tools:` list is dropped SILENTLY. So the literal
conversion would have taken a mechanical scanner from all tools to Read-only and
reported it as a ceiling fix. All eleven shipped definitions now carry
`tools: Read, Bash` or narrower plus `disallowedTools: Agent`, which is what the
seven under `workforce/agents/` already did.

2. THE CHECK THAT EXISTS TO CATCH THIS COULD NOT SEE THEM. Its glob read
`workforce/agents/*/AGENT.md`, so the four definitions bundled inside skills
were never scanned — and two of them granted `Glob, Grep` for as long as they
have shipped. Widened, and a new assertion demands `tools:` plus
`disallowedTools: Agent` and forbids `allowed-tools:` across both locations.

SKILL.md rule 3 closes "it is what the shipped panel agents already do". That
was true of the seven and false of all four. A BLOCKING gate citing an example
that does not hold is the overclaim Core Principle 6 exists to catch, so the
claim was made true rather than softened.

3. THE AUTO-MODE PROBE MATCHED A SPELLING THE CLI DOES NOT PRINT. `claude
auto-mode config` emits 77,038 B carrying `Auto-Mode` x4 and `auto-mode` x1, and
neither `autoMode` nor `auto mode` — the two literals it tested. It returned
False on every host, so preflight recommended the `--automode` remedy to readers
who already had the grant. Separators are stripped rather than alternated, so a
future respelling cannot silently reopen it.

The row's CLAIM was wrong underneath that. It read `auto mode detected ACTIVE`;
the command returns the classifier policy document, not a status field, so the
probe can establish that auto mode is configured on this HOST and nothing about
this session. It says `configured` now.

4. A MEASUREMENT NOBODY CAN SEE IS NOT A MEASUREMENT — and it was three lines,
not one. `wf-conform` prints counts, failures, advisories, adopted notes and
unreadables; a `res.add(True, …)` row is counted in the totals and never shown.
So `INV-CATREAD`, `INV-COMPANIONS` and the write-instructions row reached no
reader in exactly the state a healthy project is in, while `audit.md` Step 5d
item 2c, `verify.md`, `invariants.md` row 23 and the write-instructions row's
OWN comment ("Printed with its zero") all said to report them including the
zeroes. All three now go through `count()`, whose docstring names this failure.

`conform-companions-present` is the sharpest part and its fixture is inverted
rather than patched. The `_why` read "a PASSING row's own text is unobservable
on stdout and this half cannot assert it" and then asserted
`not: [INV-COMPANIONS]` — the defect observed, written down honestly, and
ratified as the contract. The half now asserts the row's own text, which is
strictly stronger: a regression that drops the line fails by name.

Proven by making them fail: all four defects were reintroduced at once and each
new check fired by name, with the conformance suite catching it independently.
1397 checks pass, 310/310 conformance.

bin/check: resolve the personal install the way the runtime resolves it

`bin/sync --personal` writes ${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/workforce
and this check read a hardcoded ~/.claude. On any machine that sets the variable
the two named different trees, so the check reported drift that the fix in its
own message could not clear — every run, forever.

MEASURED here while verifying the 1.64.1 batch: CLAUDE_CONFIG_DIR=~/.claude-brooke
at 1.64.1, ~/.claude at 1.63.0, `--personal` run twice, still 32 stale. The red
line had become furniture, which is the cost this project keeps recording for a
detector whose remedy does not work: it trains a reader to expect that one
failure and stop reading it.

Every shipped script already read the variable — wf-census, wf-context,
wf-widen, wf-skill-match, wf-runlength, and bin/sync itself. This file was the
sole outlier, and it is the one that ADJUDICATES the others, so the resolver it
disagreed with was the canonical one it asserts elsewhere (the wf-seed check
calls `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/workforce` canonical by name).

The failure message now names the path it actually measured rather than a
hardcoded one, so a reader on either profile can see which tree was read.

Guarded, and proven by making it fail: the assertion greps bin/check and
bin/sync for a hardcoded expansion and was run against a reintroduced one. Its
needle is ASSEMBLED from two fragments — written whole, the assertion line
matches itself and fails on the file it guards, which is exactly what the first
draft did.

Not a shipped file, so no version bump.
