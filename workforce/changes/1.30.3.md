The prune could not reach the hosts it was written for (v1.30.3)

TWO FINDINGS, both from running `/workforce update` on the maintainer's own
machine the morning after the strip-down release.

`prune_scope` rule 2 refuses to delete anything outside the skill directory
unless `.installed-external` records writing it. That rule is right — a basename
match would delete a user's own agent that happened to share a name — but the
record was added WITH the prune, in the same commit. On every host installed
before 2026-09-09 it is absent, rule 2 reads nothing, and the external files of
older releases survive forever. Which is the case the prune exists for.

MEASURED here: five wf-canary-*.md in ~/.claude/agents/ and plain-speak.md in
~/.claude/output-styles/, all six shipped by a release that no longer ships them,
all six invisible to the prune written to remove them. Five appear in the agent
menu of every session on this machine. The release meant to cut residue could not
remove its own.

Closed by a `retired` manifest flag: the explicit list of external paths this
project has ever shipped, which seeds `.installed-external` when it is absent —
and only when it is absent, because a record that exists is the authority on what
this host was written. Rule 2's safety property is unchanged: these are paths
named in the manifest, never inferred from a basename or a directory scan.

PROVED BY BREAKING IT. Against a fixture with no record: without the retired rows
all six survive the install; with them all six go and a hand-placed
my-own-agent.md beside them does not. Three assertions guard the list — every row
resolves to a destination, no path is both retired and shipped, and every
canary/style path in `git log -- manifest.txt` is either still shipped or retired.
The third is derived from history rather than memory, because a list that forgets
an entry re-opens exactly the hole it closes.

All five manifest readers learned the flag in this change, per manifest.txt's own
rule: install, install.ps1, bin/sync, bin/check, and prune_scope.

SECOND: the org chart now carries `workforce-version:`.

Every handbook already stamped the release that authored it. The chart — the file
a run opens first — did not, so "is this org older than the release I am running"
cost one read per employee, which is why no procedure asked it. org index writes
it from references/version.md, audit Step 5d branches on it before touching a
handbook, verify reports ORG-STALE. Absent is treated as older in all three and
never as equal: a chart written before the field existed is exactly the org most
in need of healing, and reading its blank as "current" is the same failure a blank
release record is. Newer-than-installed is its own stop — the skill was downgraded
under the org, and re-indexing would be a downgrade wearing a heal's clothes.
