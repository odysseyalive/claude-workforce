A capped agent still owns its shells, and the harness says so in words

MEASURED 2026-10-13, in this session: the main-Stop close-out blocked with
"Background shells still open, whose starting agent has already handed back:
b2bpv9sg8, bzcnob7u2 — started by ac2a298ca61bfa912". That agent had not handed
back. It stopped at its 80-turn cap holding both shells, resumed on its own,
read them, and delivered its report. Killing them would have destroyed the work
they were for. A blocking hook ships with zero known wrong fires, so this is
that fire.

Two readings in `closeout_facts` caused it, and the harness states the truth of
both in prose while contradicting it in the status field.

A HAND-BACK IS NOT THE TOOL'S NAME. The check read a notification as a hand-back
when its body mentioned `SubagentHandback` anywhere, and the harness mentions it
to say the opposite: "it is waiting on its own background work and will deliver
its report through SubagentHandback when that finishes", and "the subagent ended
without delivering a report through SubagentHandback, so no report was
delivered". Over the 7,300 task-notifications on this machine, 3,706 mention the
tool and only 3,364 say the report arrived; of the 342 difference, 85 are an
agent that had not reported yet and 257 carry that negation. So `handed` now
needs the harness's own positive sentence, "report was delivered to you as a
message from" — the long form, because the short phrase `report was delivered`
sits inside the negation too.

A RESUMABLE STOP IS PROGRESS, LIKE `running`. All 136 notifications carrying
"This agent stopped with background work of its own still running. It may resume
on its own" report `<status>completed</status>`, and so do all 379 turn-cap
stops. `finished` now skips both wordings, which is the same rule already applied
to a `running` notification one line above.

THE DELIVERED SENTENCE OUTRANKS THE RESUMABLE ONE, because 52 of those 136 say
both: an agent that reported AND left a shell running is the measured nine-hour
leak this check exists for, and that case must keep firing. In the record it is
`a35d0f5c81f4d67a6`, which stopped at its cap with no report at row 2852 and
delivered at row 3094 still holding `b8x3okti8`.

The signal is the harness's wording and not `at_cap`. That helper answers for the
agent whose stop is being handled, off `payload["agent_id"]`; the main Stop is
the PARENT's stop and judges agents it has no payload for, so there is no id to
read a counter for, and it would be a guarded filesystem walk per agent against
a fact already in the transcript this function is walking. The ledger's
`running`/`handoff` state answers only in a project with an issue open. This
costs a substring test.

Replayed over every main Stop on this machine, 1,532 of them: close-out fires
16 -> 11, 0 new fires, same two shells named. The five removed are all one shell
at stops where its agent had stopped at its cap with no report; it is still
reported at the first stop after that agent actually handed back. The reported
fire itself is not reachable by that replay — it serves the agent's own
transcript as it is now, and that agent resumed and recorded both shells closing
— so it was reproduced with both files cut at the stop: `WIDEN close-out —
b2bpv9sg8, bzcnob7u2 still open` at HEAD, silent after.

Fixtures, failing-first: `widen-closeout-capped-agent-still-owns-its-shells` and
`widen-closeout-no-report-delivered-is-not-a-handback` both fail before the
change and pass after; `widen-closeout-resumed-agent-that-reported-blocks` and
the existing `widen-shell-outlives-agent-blocks` were green before and stay
green, which is what keeps the genuine case pinned. The second new row kills
both mutations at once: reading the tool name or the short phrase puts the agent
in `handed`, and dropping the resumable-stop gate puts it in `finished`.

A region the session start heals is not an audit, and the banner says which

`Reaches an existing org: YES` printed the same sentence for every release that
touched a heal path: "a stale copy of something this release changed", with no
name on the something. Two things were wrong with it.

Since this session's 86c175e, `wf-commitments`' session-start carrier runs
`wf-companion.refresh_drifted`, so a DRIFTED machine-owned region is rewritten
in every project at its next session start with nobody running anything. Of the
regions that carrier covers, only `ORG-DISPATCH-CHECKPOINT` in `procedures/org.md`
is one this generator can see per-region: `WF-PRINCIPLES` and `WF-LEDGER-DOCTRINE`
live in files agents also copy outside the markers, so a change to one is
whole-file here and stays audit-side under REGIONED's own rule — a false "no"
leaves an org stale with nothing to say so. `ORG-CHAIN` stays audit-side
permanently, because `org embed` writes it into every handbook and no carrier
refreshes a handbook.

So `heal_hits` now returns which blocks moved, and the banner names each heal
path that hit and splits it: what a session start repairs, and what waits for
`/workforce audit`. `Reaches an existing org` keeps its meaning and reads YES
only when the second list is non-empty.

The rule is gated on the release version. This file regenerates all 110 bodies
every run, so applying it unconditionally would restate 109 past releases in
terms of a carrier that did not exist when they shipped — and for those a changed
region really did wait for an audit. Verified by generating every body to a
scratch directory and diffing: only 1.77.0.md moves, index.md is byte-identical,
and manifest.txt comes back byte-for-byte the same.
