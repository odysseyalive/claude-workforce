Make the provenance check fail closed: git could not answer is not "no"

Found by a security review of 862da37. `_tracked` returned `[]` when `git
ls-files` exited nonzero — no git on PATH, a corrupt or unreadable index, a
timeout — and `_usable_prior` read that as "untracked, so local-only" and applied
a `core.hooksPath` out of a record whose provenance had never been established.
The one case that is supposed to refuse was the one that failed open.

MEASURED by `githook-prior-unknown` against the pre-fix script: the heal set
core.hooksPath to the recorded `scripts/hooks` and reported it as restored. The
fixture is `githook-prior-restored` byte for byte with one corrupt index on top,
so the opposite decision is isolated to that single difference.

`_tracked` now answers None for "could not be asked", which is a third answer and
not the empty list, and BOTH callers decide what it means for them — the set is
closed, there are only two. The provenance decision refuses: the prior is not
applied, core.hooksPath is unset, and the line says `git could not say whether it
is tracked`. The report line fails closed too, which is also the honest reading:
asserting "these changes are unstaged" about files nothing could classify is a
claim the run did not measure, and silence would hide a commit the other clones
need, so it says `git could not say which of these are tracked here; if any are,
commit them`.

`bin/script-conformance` grew a `corrupt_index` key for this. `chmod` cannot
express it: the index does not exist until `init` runs, and a mode of 000 still
lets root read the file.

PROVEN with 0 VACUOUS and 0 BAD-CASE, 11 of 11 idempotence writers, bin/check

Close two symlink and provenance holes in the git-hook heal

A background security review of 73c5908 found both, and three fixtures reproduce
them before the fix.

SYMLINK-FOLLOWING WRITE (CWE-59). `os.path.exists` answers False for a DANGLING
link, so a link waiting at the target name read as a free name and `shutil.copy2`
then FOLLOWED it, writing an executable wherever it pointed — outside the hooks
directory, and outside the project if the link said so. MEASURED by
`githook-dangling-target` before the fix: the copy followed the link, failed on
the absent parent directory, and the guard copy was deleted anyway, so the hook
was lost as well as misplaced. `lexists` is the test now, a link at that name is
refused and reported, and the guard copy stays.

The source side was already refused as "not a regular file", which is the right
behaviour described as the wrong thing: it is now its own branch saying what it
is for, because copying a link reads its TARGET and writes those bytes into the
directory git runs hooks out of, with the source's mode — so a tracked link named
`post-merge` pointing at any tracked file installs that file as an executable git
hook. `githook-link-in-guard` pins it, and asserts `.git/hooks/post-merge` stays
ABSENT: nothing was carried across.

Neither path test is enough on its own, because the plan reads the directory and
the write happens afterwards, and this heal runs at session start in sessions that
can overlap. `_copy_no_follow` replaces `shutil.copy2`, which has no option for
this: both ends are opened `O_NOFOLLOW`, the destination also `O_CREAT|O_EXCL`,
the mode comes off the source descriptor, and `fchmod` sets it on that descriptor
rather than on a path. Verified by hand against the four cases — mode preserved
0o755, a dangling destination refused EEXIST, a linked source refused ELOOP, an
existing destination refused EEXIST.

UNTRUSTED CONFIG WRITE. `.settings-owned.json` is TRACKED in nsayka-wawa and
odyssey-alive, and its `prior` was handed to `git config --local core.hooksPath`.
A tracked `prior` plus a tracked `pre-commit` under it is a committed file
arranging to run its own script, installed by a heal nobody typed, at a session
start.

The rule is PROVENANCE, and it is the reviewer's, because the code offers nothing
better: every shape test passes here. The path is relative, inside the project,
and names a real directory — which is exactly what the attack looks like. An
UNTRACKED record is local-only: it was written by the `--install-hook` that
actually ran in this working tree and it arrives in no clone, so it is the only
kind whose `prior` is evidence about this machine. A tracked one is REPORTED and
not applied — a silent refusal would read exactly like finding no prior at all,
and the user is the one who knows whether that directory mattered.

The refusal cannot stop at not applying the value: the effective prior is also the
copy target, so with core.hooksPath unset the carry-across goes to the common git
dir's `hooks`, which is where git will now look. `githook-prior-tracked` asserts
that, and `githook-prior-restored` — the same tree, uncommitted — still restores,
so the fixture pair isolates the decision to provenance and nothing else. All four
measured projects record `prior: null`, so no real project changes behaviour.

The shape checks stay for the untracked case: a value beginning with `-` is an
argument injection into git's own option parser, and a NUL or a newline is not a
path.

`bin/script-conformance` grew a `links` row key for the dangling case — such a
link cannot be checked in, because `bin/check` requires every tracked fixture link
to resolve to something git carries, so it is made at run time.

Gates: 422 script-conformance cases (3 new, 1 retargeted), 16 of 16 bin/prove

Heal the stranded pin guard: a retirement that reached no project that had it

`wf-pin-check` was deleted in 1.31.0 (90fb341) and `RETIRED_HOOKS` removes its
settings row. Its other half was never a settings row at all: `--install-hook`
pointed `core.hooksPath` at `.claude/workforce/git-hooks` inside the repository
and copied the 48 KB script there, so removing the script stopped new installs
and removed the guard from no project that already had one.

MEASURED 2026-10-10 across ~/lab/*, read-only: four repositories still had the
config set and the copy on disk — nsayka-wawa, odyssey-alive, hither-lands,
playwright-mcp. In nsayka-wawa the stranded copy was walking gitignored
directories on every commit and re-adding an npm entry to
`.github/dependabot.yml` each time the user removed it (reported by session
`skul-dev`). `update` never walks a project, audit Step 6-G was a placeholder
that ran nothing, and the settings heal cannot see a hook that lives in
`git config`. A retirement nothing performs is a record of an intention.

`heal_git_hooks` is the git half of the heal that already exists, in
`wf-settings-apply` beside `heal`, so there is no new hook and no settings write:
`--heal` runs both halves, `wf-commitments`' SessionStart heal calls both, and
`verify` § Hook wiring and audit Step 6-G reach it through the `--heal` they
already run. Every machine gets it on the next `update` or `bin/sync`.

RECOGNITION IS THE CONFIG VALUE ALONE, compared `==`. apps-odyssey-alive points
`core.hooksPath` at `.claude/workforce/maintainers/git-hooks` — its own
pre-commit and commit-msg — and any looser test unwires it. The sidecar record
and the presence of the copy are deliberately NOT required: `.settings-owned.json`
is tracked in two of the four projects, so once one clone heals and commits, the
others have a record with no `git_config` and a tree with no `pre-commit` while
their own local config still points at a directory that is gone, which silently
disables the git-lfs hooks that lived in it.

The order is the part that is not obvious. Every hook that lived ONLY in the
guard directory is copied into the repository's real hooks directory BEFORE the
config is restored — git runs no hook from a directory that holds none — and
nothing is deleted until the restore is re-read off disk. `pre-commit` is deleted
only when it carries the wf-pin-check header; one that does not is somebody
else's script and is carried across instead. Any other copy is deleted only when
it is byte-identical to the one already in place; a diverged copy keeps both and
is reported, which keeps the directory. The ownership record is dropped last,
through `_render`, so the tracked sidecar keeps its own indentation. It never
commits: the report names what is unstaged, because until it is committed only
this clone is healed.

The hooks directory is resolved with `rev-parse --git-common-dir` plus `hooks`,
never a literal `.git/hooks` (wrong in a worktree and a submodule) and never
`--git-path hooks`, which is the obvious call and the wrong one: it HONOURS the
setting being removed. Measured, git 2.55.0 — it answers
`.claude/workforce/git-hooks`, so the first version compared every guard copy
against itself, called each one byte-identical, and deleted the directory it was
supposed to be emptying into. The fixtures caught it.

Refusals, each one the same test a sibling writer already makes: a `.claude`
linked out of the project is never deleted through (CWE-59, `_inside_project` —
the refusal `_project_refusal` makes for the settings half); the sidecar is
written through `write_refusal` or not at all; a recorded `prior` that starts with
`-` or carries a NUL is not a path and reads as "no recorded prior", because that
value lands in an option position of `git config` and the file is tracked on a
clone; and the apply phase takes the same `_Lock` the settings half takes, since
SessionStart fires in every session and two sessions opening one project at once
is ordinary.

Gates: 10 new `githook-*`/`commitments-heals-git-hook` fixture cases (full
stranded install, display mode byte-identical, post-pull clone, the
maintainers-shaped repo left alone, no hooksPath at all, the settled tree, a
recorded non-null prior, a diverged copy kept, a foreign pre-commit carried
across, and the SessionStart carrier), 3 `bin/check` assertions with 8
`bin/prove` cases, and a `bin/idempotence` writer row that builds its repository
at run time. `bin/script-conformance` grew a `git` row key for that: a checked-in
fixture cannot carry a nested `.git`, and the subject here is `core.hooksPath`.
The `PIN_HOOK_SETUP` constant in `bin/idempotence` was scaffolding with no reader
since 1.31.0 — the writer that replaces it removes the hook that one installed.

The fixtures were written and run RED before the heal existed: 6 of 9 failed on
the missing behaviour, and the 3 that passed are the ones asserting nothing
happens.
