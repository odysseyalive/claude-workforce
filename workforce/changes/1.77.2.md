A round is anchored to where the last one ended, so every round gets its notice

MEASURED 2026-10-13, session `68b82f98`, cap 10: the harness cut the agent on TURN 8
of round 1, not on turn 10. Two round models disagreed about what that meant.
`wf-turn-budget` scheduled round k's thresholds at `final_at(cap) + k * cap` and
`wf-widen` reported the round as `ceil(turns / cap)`; both assume a round ENDS on an
exact multiple of the cap. Round 2's final threshold was therefore booked for turn 17,
the second cut arrived before it, and the resumed agent got no final notice and wrote
no continuation brief at all — the silence this hook exists to remove, one round in.
Our count and the harness's differ whenever a turn is not a tool call, so at the
producer cap of 80 the drift opens on every resume.

So a round is anchored to where the previous one actually ended, which is a fact the
agent's own transcript records: a `SendMessage` resume appends a new PROMPT row, and
the turn count standing at that row is where the next allowance begins. `round_start`
and `round` are stored beside the count in `count.json`, and round k's thresholds are
`round_start + warn_at(cap)` and `round_start + cap - 3`.

ONE FUNCTION, BOTH HOOKS. `turn_round(state, cap)` returns the turn within the
allowance, which allowance, and where it started; `wf-turn-budget` schedules from it
and `wf-widen` reports from it through the lazy import it already had. Two numbers
derived from one function cannot disagree — two derivations of the same number did.
`counted(state, key)` is the one validator both of them read the counter with, so the
new keys are checked on the way in and on the way out.

THE CAP-MULTIPLE MODEL SURVIVES AS THE BACKSTOP, and it is what makes the anchor safe
against state the previous release wrote: `round_start` is 0 for a run that was never
cut, so round 1 behaves exactly as it did, and when the count has outrun a whole
allowance from the anchor the ceiling division answers instead — the number the last
release printed, for the state it left behind.

TWO ROWS THAT ARE NOT A PROMPT. The hook's own injection comes back in the transcript
as a `hook_additional_context` attachment carrying text, so it is excluded by name or
it would anchor the next round at the notice instead of at the cut, three turns early.
And the first prompt of a transcript is the WORK ORDER: a round cannot start on turn 0
because round 1 already did, or a re-read from the top of the file books the order
itself as an allowance and every round after it is off by one.

Four fixtures, each failing against 141106e first: the trial's own shape (cut at 8,
notice at 15, where main is silent), one turn short of it (quiet, and the anchor
recorded), a cap-80 round that ended exactly on the cap (still turn 157, so nothing
regresses), and `wf-widen`'s record agreeing with the schedule at turn 7 of 10 where
it used to say turn 5.

An issue with no items does not close over the agent that was cut working on it

The second half of the same measured run, and the one the first commit left standing:
in session 68b82f98 the session was cut before it wrote any checklist, so the issue
carried ZERO items — `undone` was empty, `judge_issue` fell through to CLOSED, and
`judge_ledger` retired the `handoff` mark as it closed. The agent that stopped
mid-work was recorded as finished and nobody was told to resume it.

An issue closed on no recorded items is a completion nobody observed, and an agent
stopping at its cap is itself the evidence that work is left — which is what the mark
means. A cut agent on an issue with no items now reads HANDOFF and the action names
the agent_id, as it does when items are open.

Replayed end to end against the trial's own shape before and after: the final
threshold marks `handoff` with eight writes counted, `SubagentStop` keeps the mark,
and the main Stop prints `i1  HANDOFF  a9 (filer) … → RESUME a9 with SendMessage`.
`widen-handoff-no-items-still-resumes` fails against the parent commit.

A cut agent keeps its hand-off mark, and a round that wrote something is not stalled

A real end-to-end run of K8 (session 68b82f98, 2026-10-13) cut a `maxTurns: 10` IC
three times and the resume line never printed once. Three defects, all measured:

* `wf-widen`'s `SubagentStop` called `agent_returned` unconditionally, and that set
  `returned` over the `handoff` the final threshold had just written. The main `Stop`
  then judged "every agent back, items open" and printed a KICKBACK. The mark now
  survives its own cut: only a stop that DELIVERED — the report its order named, with
  no UNMET row — retires it, and `agent_resumed` puts a resumed agent back to
  `running` at its first tool call, which is the only moment a `SendMessage` resume is
  visible to anything. `SubagentStop` also marks a cap hit it can see in the counter,
  which is the cut `wf-turn-budget`'s round arithmetic can miss.
* the second cut was flagged `handoff_stalled` although the agent had written eight
  more files, because the only progress signal was the issue's UNMET set and the
  session had recorded no checklist — so both marks carried the digest of the EMPTY
  set. Progress is now also the agent's own `Write`/`Edit` count, read on the SAME
  guarded transcript read that counts its turns, and stalled requires a measured
  round, a non-empty unmet set, an unchanged digest and no new writes.
* the record filed about the agent said "stopped at turn 23 of 10". The counter is
  cumulative across a resume, so that is turn 3 of the third allowance, and the line
  and the PERF body say so.

Three fixtures, two of which fail against the parent commit and the third against a
mutation that hardcodes `delivered` false; nine prove cases; `bin/check` green under a
clean HOME (1503 passed, 0 failed). The personal install at ~/.claude is now stale by
these three files and `bin/sync --personal` is the operator's to run.
