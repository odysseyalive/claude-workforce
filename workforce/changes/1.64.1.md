# 1.64.1

*Released 2026-09-17. 3 commit(s), 12 file(s) changed. Surface: changes, scripts, installer. Reaches an existing org: no.*

---

Fix two defects nc-audit reproduced re-testing 1.64.0

A DRIFT row blocked the rows around it. `wf-stamp --directives --execute`
wrote NOTHING while any drift stood, so a tree holding one missing row and one
drifted row got neither. Display mode said "Re-run with --directives --execute
to write the missing rows", `--execute` then wrote nothing, and the reader
looped — with `--restamp`, the gesture that also blesses real drift, as the only
way out.

The reach is every project at once rather than one tree. Any release that edits
workforce's own `## Directives` block drifts the sidecar row recording that
block, so after such a release `checksums --execute` was a no-op everywhere
until someone restamped by hand. nc-audit hit it on the 1.64.0 update, which
did exactly that.

The two findings are independent and now behave that way. `merged` already kept
a drifted row at its RECORDED digest, so writing the missing rows around it
re-blesses nothing — the guard was never what the refusal was protecting. Drift
ALONE still writes nothing and still exits 1, because that row has a prior
claim to erase. This is `classify`'s PRE-FOLD lesson arriving at the directives
half: a state every install enters on the same day must not have `--restamp` as
its only exit.

Second defect in the same function: the counts were computed once, before the
write, so a run that HAD written every missing row still printed
`unprotected 1`. An audit reading INV-DIRECTIVES after `--execute` read its own
successful write as a failure. The counts are now re-derived from what is on
disk, through this script's own reader — the same measurement the read-back
check already trusts — and the report says so.

Third, `wf-apply --run-canary --record-canary --execute` exited 2 demanding
--tier-limit/--c1/--c2/--by, values the process had measured seconds earlier.
`run_canary` has always chained into `record_canary`; main() tested
`--record-canary` first, so the chain was unreachable whenever both flags were
typed — which the usage block invites. Order swapped. A bare `--record-canary`
still demands every field: that form is the hand-entry path, and refusing a
hand-composed measurement file is why the recorder exists.

Proven by making them fail: the three bin/check probes and the new
`stampdir-drift-plus-missing` conformance case were run against the unfixed
scripts and each reported the defect in its own words. `stampdir-orphan` now
asserts both halves of the report — the `! ORPHAN ROW` finding line still names
what was dropped, and `orphan 0` is the state after the write.
