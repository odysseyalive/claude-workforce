The session boundary is a judgement, so it is a command (v1.47.0)

ASKED FOR by the user, correcting the author's plan to enforce this with a commit
hook: "It should trigger that we're getting close to the end of our session and you
should ask whether you would like all the commits to be added to the next version
bump ... if it's a skill that does this, you'll know to run the skill or not or I can
ask for the skill to run. That's better than making a hook."

AND THEY ARE RIGHT ABOUT WHY. A commit hook fires on every commit and can only ever
say "you bumped without a change record". It cannot know a session is ending, which is
the one moment this decision needs making — and by the time a hook could object, the
commits it should have gathered are already spread across a dozen version numbers.

MEASURED ON THIS SESSION, which is the case that produced the request. Twelve version
bumps — 1.39.0 through 1.46.0 — each a real release with its own number, none with a
change record, because nothing knew the work was one body of work until it was over.
An auditor reading `workforce/changes/` would have found nothing from a day that added
nine hook registrations across five events and rebuilt evaluation twice.

`/workforce dev wrap` censuses the commits since the last bump, names how many versions
were bumped inside them, and ASKS whether they are one release or several — because
which shape is correct depends on whether the work was one thing, and only the user
knows that. Deciding it silently would be the same self-assessment every other
mechanism this week was built to remove. It writes the change record either way, and it
never pushes and never tags: a push reaches every machine that runs `update` and stays
the user's gesture.

IT IS INVOCABLE BY EITHER SIDE, which is the half a hook cannot do. The operator runs
it on finalizing language — "that'll be the last thing", "commit everything and I'll
push later", "I need to restart this session" — and the user runs it by name when the
operator misses. A miss is cheap and a false fire is cheaper, because the command asks
before it writes.

It is directive two read literally: mechanism where mechanism works, judgement where
judgement is needed, and *when has this session ended* is a judgement.

ALSO IN THIS RELEASE. `githooks/pre-commit` is restored. It was deleted by 90fb341 —
the same simplification strip that orphaned the four dead scripts healed earlier today
— while `core.hooksPath` kept pointing at the now-empty directory, so git looked there,
found nothing, and said nothing. The version-bump guard has not run since v1.31.0,
which is why twelve bumps sailed through. It is a NARROWER thing than `wrap` and not a
substitute for it: it refuses a bump whose two version strings disagree or whose change
record is absent. Verified firing by bumping to a fake 1.99.0 and watching the commit
be refused.

The change archive is regenerated whole: 64 records, every release, bodies derived from
the commit messages between one bump and the next.

The change record for everything this session built (v1.46.0)

ASKED FOR by the user, closing the session: "hopefully what we have in place includes
information from the commits for the appropriate version number so that's mainly for
the auditor."

IT DID NOT. Enumerated rather than assumed: all TWELVE versions built in this session
— 1.39.0 through 1.46.0 — had no change record at all. The archive stopped at 1.38.0,
so an auditor reading `workforce/changes/` would have seen nothing from a day that
produced nine hook registrations across five events, retired an invented score,
rebuilt evaluation around an independent jury, and healed four dangling references the
previous release reported healing and missed.

Regenerated whole, which is how this archive works: 63 files, 62 releases, bodies
derived from the commit messages between one bump and the next. Nothing is authored
twice — the why-this-changed prose already exists in the commits, and a record
rewritten by hand is a second canonical text that drifts from the first.

WHAT THE AUDITOR NOW READS, per release: the date, the commit and file counts, the
SURFACE the release touched (derived from the paths its commits changed, so it cannot
drift from the change), and whether an existing org holds a copy of something the
release altered. `1.39.1` is the one row from this session marked **yes** — the
healing pass rewrote audit, verify and hooks, so installing the skill is not the whole
update for a project that already has an org.

Not tagged, and deliberately so. The version NUMBER is recorded in `version.md` and
`SKILL.md` and now in the archive; git tags are a separate question the user has left
for later, and the installer fetches `main` rather than a tag, so nothing depends on
them today.
