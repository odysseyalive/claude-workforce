The hook that forced a version number per commit is gone (v1.47.1)

ASKED FOR by the user: "let's remove it again. I would rather not spam version numbers
for every commit that happens. It's a bad model. I'd like to do it like we just
discussed."

AND IT WAS NOT MERELY REDUNDANT WITH `wrap` — IT MANDATED THE THING `wrap` FIXES. As a
git hook, `bin/pre-commit-version` refuses any commit touching a shipped file unless
`WORKFORCE-VERSION` advances. Every commit therefore becomes a release, and a working
session becomes a column of version numbers. Restoring it one release ago would have
locked in exactly the twelve-numbers-a-day behaviour the previous release was written
to end.

REMOVED: `githooks/pre-commit` deleted, `core.hooksPath` unset. `bin/pre-commit-version`
stays on disk and stays WIRED TO NOTHING — it is still callable for a release that
genuinely is one, which is the case `wrap` produces, and the reason it must not fire
automatically is now stated where a reader will meet it rather than left as an absence.

The author restored that hook one release ago having been told a skill was the better
model, on the reasoning that it had been deleted by accident rather than by decision.
That reasoning was right about the history and wrong about the design: a guard removed
by accident can still be a guard that should not come back.

MEMORY CORRECTED, because a stored rule that is now false is worse than none. The
project memory said shipped-file edits must advance the version or the commit hook
blocks. It now says one bump per SESSION via `/workforce dev wrap`, records that this
reverses the earlier rule, and names why: a commit hook fires per commit and cannot
know a session is ending, which is the one moment the decision needs making.
