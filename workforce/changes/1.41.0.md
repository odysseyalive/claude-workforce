The alarm had no response (v1.41.0)

ASKED FOR by the user, twice, and the second time with confidence draining: "Did the
widening architecture get built?" then "I'm kind of losing confidence here." The
honest answer was no. Enumerating the code settled it — every `spawn` in `wf-widen`
was a comment or a name in a set, and nothing in it started a process, ran a search,
or called anything.

WHAT HAD BEEN BUILT WAS THREE PIECES OF ALARM AND NO RESPONSE. Score the turn on the
senses its task needs: built. Tag the ask up front so the sense is known before the
answer: built. Block the stop when a required sense went unopened: built — and
MEASURED over 92 stop summaries, it ran on every one, errored on none, and blocked on
ZERO. What a block does is hand back a list of instruments the turn did not use, and
then rely on that same turn to go and use them, which is the decision-from-inside the
whole mechanism exists to remove.

`wf-widen-agent` IS THE RESPONSE. A `type: "agent"` Stop hook — the only hook in this
distribution that acts rather than reports. A command hook has no model: it can decide
a sense went unopened and it can never open one. This spawns a reader carrying
Read/Grep/Glob and none of the finishing turn's context, opens the channel that was
left shut — the git record and `changes/` for hearing, running the thing for touch,
enumerating for taste — and returns what it found as the next instruction. A spawn is
not self-checking, and three of the ten recorded escapes in this project came from
one; what kept it from firing was always that spawning required a decision made from
inside.

CHEAP DECIDES, EXPENSIVE ACTS. `wf-widen` is deterministic and free and runs every
turn; when it blocks it writes a flag naming the unopened sense. The agent hook reads
that flag and returns `ok: true` immediately when there is none, so the subagent is
spawned only on the turns that earned one. `wf-task-tag` clears the flag at the head
of every turn, so one can never outlive the turn that raised it and send a reader
after a question the user has moved past.

THE MISSING COMPLETENESS CHECK, which is the user's other question: "I thought there's
always a check to make sure that all the components are finished. Where did that
break?" It did not break — it was never in scope. `bin/check`'s producer-has-a-reader
invariant operates over things that EXIST, and `wf-widen` passed it perfectly while
being half a mechanism: it had a reference, an assertion and four fixtures. Nothing
anywhere checks the set of things that were SPECIFIED, and a four-part design with
three parts built leaves no artifact whose absence anything can notice.

So the directive that covers exactly this — "A DETECTOR SHIPS WITH ITS FIX. Detection
alone is not a deliverable", in SKILL.md since 2026-08-05 — is now enforced for hooks,
over the one thing a missing actor DOES leave behind: a hand-off file that is written
and never read. Structural, not prose: matching hooks.md for words like "reports"
would be a substring test over English with no measured error rate, the shape that
retired `wf-speak-guard` at 7.0%.

THE FIRST VERSION OF THAT CHECK WAS VACUOUS AND ONLY BREAKING IT ON PURPOSE FOUND IT.
It counted any hook that named the artifact and called `os.remove` as a reader, so
`wf-task-tag` — which only CLEARS the flag — satisfied the requirement for an actor.
Deleting is not acting; a clearer is housekeeping. It now passes whole and fails when
the actor is removed, verified both ways.

TWO AGENT-HOOK BUGS, both found by running the thing rather than reasoning about it.
Agent hooks carry no `command`, so `_same_command` answered False forever: presence
detection would have re-registered the hook on every `--wire-defaults`, leaving a
duplicate per run, each spawning its own subagent at every Stop. And the post-write
re-read used the same broken test, so a CORRECT write of the agent hook came back
"UNVERIFIED — re-read found 0". The write was fine and the instrument was wrong, which
is the worse of the two: this verifier exists so that a settings write is never
believed without being re-read, and one that cries failure on a good write teaches its
reader to ignore it. Both call sites now share `_same_agent`, and the assertion
requires BOTH.
