Record that the out-of-pool budget row has never executed, and what fires it

The rendering table's last row — a recorded model OUTSIDE the statics pool,
placed last as `(current — not in the pool)` — is the only row there with no
observation behind it. A full six-question setup measured 2026-09-17 returned
`rendered 6 of 6 owed · 6 messages · in order` with every recorded value in the
pool, so the branch was never entered. The customer reported that gap rather
than letting `6 of 6 · in order` read as full coverage, which is the right
instinct: a pass on a branch that never executed is the defect this project
keeps finding in its own fixtures.

WHAT MAKES IT WORTH RECORDING IS THE TRIGGER, which is not an audit. A
re-audit cannot move a recorded value out of the pool on its own — RETIRING A
STATICS ROW in `org-config.template.md` is the event that activates this row,
simultaneously, in every org that had recorded the retired value. So the next
release that retires a model owes this row its first real exercise, and the
maintainer doing it should expect to be its first reader. Stated where the rule
lives rather than in `bin/check`, because the rendering is executor-followed and
there is no producer script a fixture could run against.
