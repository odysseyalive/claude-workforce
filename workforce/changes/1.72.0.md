A row id could forge the inbox marker and make a live defect disappear from --list

FOUND BY /security-evaluator on the change it reviewed. Both values written into
`wf-upstream`'s marker comment came from outside the script, and that comment is
MACHINE-READ: `header_fields` parses it, and `--list` and `--resolve` act on its
`status` field.

    <!-- wf-upstream: v1 | project=<slug> | row=<id> | status=open -->

`render()` wrote the RAW `row["id"]` there. `deferred.md` is a file an agent edits, so
that cell is untrusted input to markup — a value carrying `-->` closes the comment
early and puts the rest of the line into the rendered document, and a crafted id
emitting a second `status=resolved` pair makes a real OPEN row vanish from the one
surface built to surface it. That is the forged field that matters: not a defacement,
a live defect silently removed from the maintainer's queue. `--version` is the second
such value and was unconstrained for the same reason.

Same output-encoding class, and the same remedy, as `wf-catalog.house_write`'s
constraint on `.current-run`, which exists because `x -->` in that file would close
the provenance comment early. The INDEX is scrubbed through the `safe_part` allow-list
already used for the filename; `--version` is held to
`[A-Za-z0-9][A-Za-z0-9.+_-]{0,39}` — wider than strict semver, so `1.72.0-rc1` still
closes a row, and narrower than free text.

**THE EVIDENCE IS NOT SCRUBBED.** The verbatim row still goes into the fenced block
below the marker, unaltered, because that is where untrusted text belongs and because
a maintainer reading somebody else's finding must not be handed a sanitised paraphrase
of it. The new fixture proves both halves at once: its `y` row's finding cell literally
contains the string `status=resolved`, which survives verbatim in the block and never
appears in the marker.

`semgrep --config=p/python --config=p/security-audit` is clean on both new scripts, and
was clean before this fix too — the finding came from tracing source to sink by hand,
which is what the taxonomy asks for. No other class fired: no shell, no eval, no
deserialization, no network, and the one subprocess call takes a list argv with no
shell.

Fixture `upstream-forged-marker`, `bin/check` assertion
`upstream: every value written into the machine-read marker is constrained` (positive
AND negative — the positive alone passes on a file that builds the safe key and then
writes the raw cell anyway), and a `bin/prove` case that deletes the version guard.

Gates: bin/check 1427 passed 0 failed · script-conformance 362/362 ·
bin/prove "upstream: every value" 1 of 1 proven by breaking.

The corpus builds the environment its cases run under, so a golden cannot move with the session

MEASURED on the first corpus run from a second session: `bin/corpus run` FAILED on
`university` with no code change. `wf-preflight` reports the env vars that could
override an employee's frontmatter, so `CLAUDE_EFFORT=high` went into the golden and
`CLAUDE_EFFORT=medium` came out of the next run. **A known false fire is not
shippable** — a suite that fires on the operator's shell is one nobody keeps green,
and this one is wired into `bin/check`.

THE CLASS, NOT THE FIELD. Deleting the one variable that bit would have left
`CLAUDE_CODE_SUBAGENT_MODEL`, `ANTHROPIC_MODEL`, a `TZ` that shifts every printed
date by a day, and a `LANG` that changes how a locale-aware sort orders rows — each a
diff nobody changed any code to cause. So the environment is BUILT rather than
filtered:

    ENV_KEEP  PATH, TMPDIR, SYSTEMROOT, COMSPEC — what a subprocess needs
    ENV_PIN   TZ=UTC, LANG/LC_ALL=C.UTF-8, LANGUAGE=, COLUMNS=80, TERM=dumb, NO_COLOR=1
    then      HOME and CLAUDE_CONFIG_DIR, pointed at the throwaway install

Everything else is absent, `CLAUDE_*` and `ANTHROPIC_*` included — which is a state a
script has to handle anyway, since an env var it reads is one a fresh host may not
have set. The throwaway install is now built under the same env, or the golden moves
with the session one level further back.

`PYTHONHASHSEED` IS DELIBERATELY NOT PINNED. A fixed seed would make set-iteration
order stable and hide exactly the defect this corpus found on its first run —
`wf-census` printing its rows in `os.walk` order, two runs of one unchanged tree
swapping two of them. That would turn a caught regression into a silent one.

THE CHECK RUNS IT TWICE, under two deliberately different sessions' worth of
environment — a different effort, a different subagent model, a third model variable,
a different timezone, a different locale. One run answers "did the behaviour change";
only the pair answers "can this suite tell". The assertion is renamed to say so:
`corpus: the display-mode scripts say the same thing on a real org, whatever the
session`.

University's goldens were re-recorded once under the scrubbed env. Verified: two runs
at the same effort, one with `CLAUDE_EFFORT=low` plus three other hostile vars, and
one with no `CLAUDE_*` in the environment at all — 26 cases, 0 diffs, every time.
`CLAUDE_EFFORT=medium HOME=<tempdir> bin/check` → 1426 passed, 0 failed.

THE QUEUE HAD A WRITER AND NO READER. `references/deferred.md` keeps exactly two
categories of row alive across runs, and one is "a fix in another repository" — in
practice, this distribution. That file names its own gap in the same breath: the
closing mechanism was "a person noticing the paragraph and opening a session by
hand", which it calls **a rule with a reader and no producer**.

MEASURED 2026-09-25 on `university`, run audit-20260925T180537Z: seven surviving
rows, every one a defect in THIS repository, three of them carried through three or
more audits. Row 7 — no shipped script writes the `WF-HOUSE-RULES` region — was
re-verified and re-filed on 2026-08-20, 2026-09-14 and 2026-09-25, and the third run
gave up and wrote the region by hand. Rows 2 and 3 asked the install to ship catalog
rows that are the project's own, so they could never have been discharged as written.
Nothing on the workforce side had read any of it.

    wf-upstream --root <tree>                 report which rows belong upstream
    wf-upstream --root <tree> --execute       file one file per row into the inbox
    wf-upstream --list [--json]               open rows (what a dev session reads)
    wf-upstream --resolve <id> --version X    name the release that should close it

THE THREE PATHS (`references/enforcement.md`), each with its own assertion:
`manifest.txt` ships the producer, `audit` Step 7 runs it in the same step that writes
`deferred.md`, and `verify` reports the inbox with `INV-UPSTREAM` including at zero —
a project with no workforce defects to report is the state this is trying to reach,
and it has to look different from a project whose queue was never read. The READER is
`/workforce dev`, which lists open rows at startup in § Dev Path Discipline.

A TOLERANT PARSER, BECAUSE BOTH SHAPES ARE REAL. `deferred.md` § Location and shape
specifies `| id | opened | … | state |`, and every real queue this project has ever
produced is the other thing: a run report with `##` sections over `| # | Finding |
Evidence | What discharges it |`. A parser accepting only the specified shape reads
university's seven rows as zero — the same failure as the one being fixed, one layer
down. Columns resolve by header name, state by section heading, and a queue in neither
shape says so: `0 rows` and `could not read the rows` never print the same line.

Rows are classified `strict` when they obey the BLOCKING rule that an other-repository
cell names the repository's absolute path, and `loose` when they only name the category
in words — which every real row does. Both are filed, with which signal fired, because
a loosely-matched row is one whose reproduction a maintainer still has to reconstruct.
A `Discharged this run` section is skipped, and a canary `UNAVAILABLE` row is skipped
too: that is the OTHER surviving category, a measured host limit, and filing it here
would put the host's problem in this repository's inbox.

THE FILENAME IS BUILT FROM PROJECT DATA, so it is scrubbed AND the write is measured.
The row id comes from a Markdown cell in a file an agent edits, joined to a path under
the personal config root. An allow-list reduces slug and row id to one safe component
each; then `dirname(realpath(path)) == realpath(inbox)` measures where the write would
actually land, because a scrubber is a claim about what it removed and a prefix test
passes a path one directory deeper. Proven on a fixture carrying `../../../../../../tmp/…`,
`/etc/shadow` and shell metacharacters as row ids: all three land inside the inbox
under scrubbed names and nothing is written outside it.

IT NEVER CLOSES THE DOWNSTREAM ROW, and the script, the procedure and the check all
say so. `deferred.md`: the row closes when the downstream run RE-RUNS its own
reproduction and watches it pass, never by an upstream report asserting the fix
shipped. `--resolve` records a claim for that project's next audit to TEST. Idempotent
by project and row id — the next audit rewrites the same file rather than filing a
second copy, and a row a maintainer already resolved is left resolved, or every audit
would silently reopen it.

`gen-changes` DOES NOT LIST RESOLVED ROWS, and that is a decision, not an omission.
It writes `workforce/changes/<version>.md`, which is committed, and this repository is
public; an inbox entry holds a downstream project's slug and its row verbatim. `wrap`
Step 1 prints them to the operator instead — same trade `corpus/` already refuses.

Fixtures (5): the real report shape with a discharged section, the same tree under
--execute asserted on disk, the canonical shape with its three outcomes, hostile row
ids, and a queue in neither shape. All five fail against HEAD, where the script does
not exist.

A local-only regression corpus, so a release is measured against a real org and not only against trees we wrote

WHY. Every other gate here runs against fixtures this project authored. 1.71.0
passed 1,411 checks and 726 prove cases, shipped, and on the first real org it was
pointed at left 505 false readers; its new `--house-rules` producer crashed with
`NameError: name 'body' is not defined` on every project that already carried a
region, a branch no fixture could reach because every fixture was a first-write
tree. Both were found by hand, by copying one real project and running the command.
`bin/corpus` is that gesture made mechanical.

    bin/corpus snapshot <project-dir>   copies .claude/ (+ CLAUDE.md) into corpus/<name>/
    bin/corpus list                     snapshots, and the 26 cases with their citations
    bin/corpus run                      every case against a throwaway copy, diffed
    bin/corpus run --case <label>       one case
    bin/corpus run --accept             re-record the goldens

LOCAL ONLY, AND NEVER COMMITTED. `corpus/` is gitignored and a new `bin/check`
assertion fails if anything under it is tracked — an ignore rule is not an
assertion, `git add -f` beats it, and the fixtures block exists because exactly
that happened in the other direction. This repository is public; a snapshot is
another project's handbooks, prompts and notes verbatim. With no snapshots
`bin/corpus run` prints one SKIPPED line and exits 0, so a fresh clone stays green,
and `corpus` joined `bin/prove`'s IGNORED_DIRS so an 18 MB snapshot is not copied
once per case.

NOTHING TOUCHES THE REAL PROJECT. `snapshot` reads it once; `run` copies the
snapshot and removes the copy in a finally, so a failing case, a traceback and a
Ctrl-C all still clean up.

THE CASE LIST IS DERIVED. Each of the 26 rows cites the `audit.md` or
`audit-setup.md` line that names its script, and `bin/check` re-reads every
citation — a procedure that stops naming a script, or renames it, fails there
instead of leaving this list measuring one author's memory of the audit. It caught
four of my own guesses immediately, and `wf-ledger` was dropped because no audit
procedure names it: a case for it would have been this file inventing a step.

THREE THINGS MAKE A DIFF MEAN SOMETHING, and two of them were wrong first:

- The install side is a throwaway `bin/sync --personal` of the checkout under test.
  The first version pointed CLAUDE_CONFIG_DIR at the snapshot's own `.claude/`,
  which collapses personal and project scope onto one directory — `--migrate` then
  answered `no-copy · nothing to migrate` for all five kinds on a tree holding five
  copies, and the golden recorded that. A 1.70.0 checkout reproduced it exactly: a
  green case over a command that had done nothing.
- The operator's HOME is not an input. `wf-census` counted the developer's own
  `~/.claude/agents/`, and `wf-context` charged 3,853 B for a CLAUDE.md in the
  directory above this repository. Every case now runs under a throwaway HOME whose
  only content is the install, with the copy inside it, so the inherited-CLAUDE.md
  chain is the snapshot's own.
- A traceback is a failure whatever the exit code says. A golden recorded over a
  crash would make the crash the expected output, which is the worst thing a
  regression corpus can do.

TWO DEFECTS FOUND WHILE BUILDING IT, both fixed here:

1. `wf-census`, `wf-context` and `wf-conform` all exited 2 on the first snapshot —
   `university` registers two employees as symlinks into a subdirectory project, and
   copied as links they dangled. `materialise_links` replaces a link that leaves
   `.claude/` but stays inside the project with its content, and leaves the other two
   alone: one points inside `.claude/` and still resolves, and one is a negative
   fixture whose whole subject is a link out of the tree (`-> /etc/hostname`).
   Resolving that one would silence the assertion it exists for.

2. `wf-census`'s report row order was the filesystem's. Its five row sets are filled

A catalog grep reads the layer a retirement kept, and every hit says which layer answered

MEASURED on a copy of `university` with both `--migrate --execute` and
`--house-rules --execute` already run: `wf-catalog --kind image --grep
'Consistent edge quality'` answered `no match` while the row sat at
`.claude/skills/image-eval/references/watercolor.md:16` — a file the same
migration had printed `STAYS … cited by` five readers.

Only the rows of a file that GOES are lifted into CATALOG-ANCHOR.md, so a kept
file's rows lived in no layer the resolver read: it read the install plus the
anchor and stopped. For three consecutive audits that project's own grader was
told its rule did not exist, and the finding was carried as deferred row 3 with
"the install ships these rows" as the only discharge — which was never going to
happen, because the rows are the project's.

`--grep` now reads four layers in precedence order and every hit carries the
layer that answered:

    install:<rel>                        the shipped corpus `update` advances
    additions:<file>                     workforce's own authored slot
    project:<skill>/CATALOG-ANCHOR.md    the layer that outranks the corpus
    copy:<skill>/<rel>                   the .md a retirement KEPT

The source list moved into `grep_sources`, which is also what made the layering
statable. Three properties it carries, each for a measured reason:

- The resolved corpus is labelled by where it RESOLVED FROM, so with no install
  reachable it reads `copy:` rather than an `install:` that would be a lie.
- `classify` decides what "kept" means, not "whatever is still on disk". Before a
  migration the copy still holds the files that duplicate the install, and
  searching those would print every shipped row a second time from a path that is
  about to stop existing.
- A refusal now names every layer it searched and the file count in each. A
  refusal naming one layer of four reads as absence, which is exactly how this
  defect survived three audits.

Verified on a university copy: the image row answers under `copy:`, and rows 2
and 3 of that project's queue — `Productive tangent minimum/absent` and `Line X:`
— now resolve too, the second from a kept `agents/*/AGENT.md`.

Fixture `catalog-grep-reads-cited-copy-file` reproduces the shape exactly: one
removable file byte-identical to the install's, one file with no install
counterpart that STAYS because an employee cites it. It asserts both labels and
that the removable duplicate is NOT searched a second time from the copy.

`bin/prove` L630's case was retargeted rather than deleted: the one-line
comprehension it broke became a loop, and `bin/check` caught the dead case.
