A verdict that blamed the assertion when the mutation was at fault

ASKED FOR by the user, twice, and the second time with the receipts: "Can we
improve the way prove gets applied?" then "This has happened more than once now"
and "we talked about focused testing too."

Both were right and I had been treating symptoms — retargeting cases by hand, four
times in one session, re-deriving the same conclusion each time.

ONE — THREE VERDICTS, NOT TWO. `prove` called a case VACUOUS whenever the named
check did not fire, regardless of why, and `len(fails)` had told the two apart the
whole time:

  VACUOUS    the mutation landed cleanly, check ran, and the assertion STILL
             PASSED. A finding about the ASSERTION. It is testing nothing and it
             should stop a release.
  BAD-CASE   the mutation wrecked the file, so check failed on OTHER assertions and
             the named one never ran. A finding about the CASE. The assertion is
             unproven, not disproven, and the fix is to retarget at a literal.

Collapsing them costs twice. It sends a maintainer to fix an assertion that was
never broken — four times today — and worse, A REAL VACUOUS ASSERTION HIDES AMONG
THEM, because the label that should stop a release reads identically to the one
that means "your case is wrong."

IT FOUND ONE WITHIN A MINUTE OF SHIPPING, in my own work from an hour earlier. The
`"senses": []` case had been filed under the blind-sample check and reported PROVEN
— only because the assertion that actually reads that literal did not exist yet.
Once it did, the case became a BAD-CASE and said so. It was then filed under a
SECOND wrong name before landing on `wf-task-tag names the sense and never blocks
the ask`, which is the check that reads it. A case pointed at the wrong assertion
proves nothing about either, and nothing had been able to say that out loud.

TWO — `--since <ref>`, WHICH IS THE ONE THAT CHANGES THE DAY. The name filter added
this morning still requires knowing which assertion an edit touched. After a change
the real question is "which cases point at a file I just modified", and git already
knows. Every case names its target, so the selection is exact and needs no new
bookkeeping. MEASURED: 19 s against ~30 minutes for the full 722.

A gate that costs half an hour is run a few times a day. One that costs twenty
seconds is run after every edit, which is the difference between catching a vacuous
assertion when you wrote it and catching it at release.

THREE — `--help`, because asking this tool how to use it RAN IT. The flag starts
with `-` so it was not a name filter, fell through to a full run, and did it twice
while I was writing the usage text. It now prints and exits, placed above the
baseline check rather than below it. A reader asking how something works must never
be answered by running it.

ONE BUG IN MY OWN CHANGE, caught by running it rather than reading it: `--since
HEAD` put `HEAD` into the name filter, so a focused run selected three cases and
then reported "no case name matches HEAD". A flag that takes a value has to skip
that value.
