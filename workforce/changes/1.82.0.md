Each message's asks checklist is its own file, so a queued submit never rewrites the running turn's

da98d16's known limit. A queued message's UserPromptSubmit fires before
the running turn's Stop, and wf-asks.<sid>.json was one file per session.
Measured on da98d16's code, in the real orders:
- turn 1 writes its two items, then submit 2: the submit replaced the file
  with message 2's empty list, so Stop 1 handed the juror no checklist for
  turn 1;
- submit 2, then turn 1 writes its items: the late write replaced message
  2's fresh list. Stop 1 absorbed it onto i1, and Stop 2 absorbed it again
  onto i2, which printed "i2  KICKBACK  Crash cause" and gave message 2's
  juror turn 1's checklist.

Mechanism: the checklist path takes the message's issue id,
wf-asks.<sid>.<issue>.json. The record carries it as `key`. Each submit
tells the session that path, so each turn writes its own file. Each Stop
reads the file of the record answered_record picked. A record with no key
(carry-only, or one an older release wrote) names the bare file, as before.
The submit keeps the outgoing file while its keyed record is un-ended. A
later submit removes it once a Stop has ended it, along with any ended
`earlier` record's file. wf-widen.checklist spells out both names, because
wf-live pairs the writer and the reader by that literal.

Why not keep a copy in the `earlier` record: when the items are written
after submit 2, the copy taken at submit 2 is empty. Nothing on disk at
Stop 1 then says whose list the one file holds, because the file's own
fields are the session's to edit.

Also:
- bin/script-conformance: a `before` step can be a `write`. It writes to
  the first `path_rx` match in step `path_from`'s output, which is the path
  that hook told the session. So each release is tested at the path it
  told.
- hooks.md names the per-message file.
- Two carried-list cases now read wf-asks.s1.i3.json, the new message's
  file.

Three cases. written-before-submit-2-stop-1 and
written-after-submit-2-stop-2 fail with da98d16's hooks and pass here.
written-before-submit-2-stop-2 runs the whole order through Stop 2 and

Stop judges the message its turn answered, not the one queued behind it

A queued message's UserPromptSubmit fires at enqueue, before the running
turn's Stop (/home/francis/Work b6047346: 17:21:55 against 17:21:59). The
tag kept one record per slot, so Stop 1 read message 2's record: the jury
got "please reach out to @mutze-dev..." as turn 1's ask, and WORK tracked

Mechanism: the tag keeps the records it replaces as `earlier` (newest
first, capped at 3). Its top-level fields are still the newest record, so
the next submit's previous_checklist, SubagentStop slots and old
single-slot files read the same as before. At a main Stop, wf-widen's
task_tag picks the record by matching the turn's own user row in the
transcript. It walks back from the last assistant row, skips tool results,
tries isMeta rows without stopping on them, and stops at the first typed
row or at a stop_hook_summary/turn_duration row. Text and not prompt_id,
because the transcript rows hold the verbatim prompt. Whether the payload's
prompt_id already names the queued message at an enqueue-time submit has
not been measured. A queued message has no user row until its own turn
starts. One delivered mid-turn arrives as a queued_command attachment and
never gets a row. If nothing matches, the newest record is used, as today.

Also:
- mark_ended marks the picked record, any record holding the same
  checklist, and every older record.
- track_message supersedes fallbacks only on issues opened before the
  target, so the queued message's seeded item survives Stop 1.
- widen removes a flag an earlier Stop raised and finished with
  (`audited`). The submit-time clear ran before Stop 1 raised it.
- bin/script-conformance: a `before` step list runs earlier hook events in
  the same tree, and --touching follows the step scripts.

Four cases. stop-1, stop-2 and heals-a-single-slot-tag fail with main's
