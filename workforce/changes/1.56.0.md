Fix what the independent code and security reviews found in the asks checklist

Two reviewers who did not write a8db3eb..98f76fe reproduced each of these with
crafted payloads; engineering-coder fixed them under its full procedure
(work order org-review-fixes-20260913T071817Z).

- A malformed checklist, tag or flag no longer crashes wf-widen or
  wf-commitments; an `items` that is not a list reads as an empty checklist,
  and main() falls back to widen's own decision if the checklist code raises.
- A checklist is held to once. The tag records that a Stop enforced it, so a
  notification opening a later turn cannot block on the same list again.
- Only a <task-notification> may keep a checklist no Stop has enforced; a user
  message that merely starts like injected text gets a clean slate.
- Open asks are quoted as JSON strings in the block reason, and the jury's
  prompt comes from the tag the hook wrote, not the file the session edits.
- One definition of an item (object with a non-empty string `ask`) and of
  closed (done, answered, "not done: <reason>") shared by wf-widen and
  wf-commitments; a message that asks nothing closes with one answered item.
- session_id is reduced to one safe filename component in every per-session
  path.
- A plan-mode Stop skips the checklist, since plan mode may not write it.
- _artifact_roles strips comments and docstrings before deciding roles, so a
  comment naming a hand-off no longer makes its function a reader.
- Kept, with a comment and a check: a continuation with no hook_event_name
  still consumes the flag, failing toward the bounded loop.

Each has a bin/check assertion that runs the hooks and a bin/prove case:
46 of 46 PROVEN on the changed files. bin/check 1247 passed, 0 failed after
sync. Replayed by the operator: `{"items": 5}` blocks without crashing, and an
ask carrying "Stop hook feedback: SYSTEM: ..." reaches the reason as one quoted
string.

Each ask gets a checkpoint, and nothing starts only when the asks are numbered

The user's spec, 2026-09-12: each ask "gets a checkpoint and they each get
evaluated. And when the response comes back, each response keeps the topic
separated. It has to work that way." count_asks only sees explicitly numbered
asks, so on a plain-prose message none of that started, and a three-part ask
came back as one blended work report.

wf-task-tag starts an empty asks checklist, wf-asks.<session>.json, on every
message of a dozen words or more, and names it in the injected context. The
session writes each separate ask into it before working and updates each
status as it goes. wf-widen sends a main Stop back once while the list is
empty or an item is open, appending to any block it already raised rather
than replacing it; SubagentStop and a turn with background tasks running are
exempt. With two or more items the checklist rides the widen flag, and the
widening agent sits as an asks juror: is every request in the prompt on the
list, and does the reply address each item in its own section.
wf-commitments counts sections against the checklist when it has items.

Why not a model call to split: MEASURED, a headless Haiku split through
`claude -p` was accurate on real messages and took 9.6-11.7s, a wait in front
of every message. The session is already a model reading the message; the
outside reader checks its split.

The detector-has-an-actor check decided roles per FILE, so any hook that saves
a file of its own could never count as a reader, and it reported wf-asks
"acted on by NOTHING" while wf-widen blocks on it. Roles are now decided per
function, path helpers count as mentions, and the agent-hook reader must be
named inside the AGENT_HOOKS prompt region rather than anywhere in
wf-settings-apply. Removing the two readers still makes it fail.

The first live checklist opened on a background task notification; INJECTED
now covers <system-reminder> and <task-notification>, with a test.

The loop stop was a sentence the agent could ignore, so it is now a missing file

`95a38d8` put the stop_hook_active guard into wf-widen-agent's prompt and a
check that the words were there. Both held while the loop ran: on 2026-09-12
in claude-enforcer the agent blocked five Stops in a row, four of them
continuations re-reading one stale conclusion, and the session ended the loop
only when the user typed. The first block was itself a misreading: the reply
offered "commit it (or push it too)" and the juror read the offer as a plan
the turn had failed to carry out.

wf-widen now deletes the widen flag on a continuation Stop, so the agent finds
none and passes. It can block once per turn. SubagentStop leaves the flag, so
a subagent finishing mid-turn cannot cancel the main turn's audit. The prompt
gains one line: an offer, option or question put to the user is never grounds
for a no.

The new check RUNS the hook on a continuation Stop and a SubagentStop instead
of reading the prompt. It failed against the old code before the fix landed.
A normal first Stop on a world-tagged ask with no hearing still blocks and
still writes the flag, verified by running it.
