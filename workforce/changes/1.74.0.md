A carve-out sentence does not say which repository

`wf-upstream` filed a deferred row into the maintainer's inbox on the strength of
a FILE-LEVEL sentence — "a fix that lies in another repository" — which names no
repository at all.

MEASURED 2026-10-02 on this machine's real inbox: of thirteen rows filed from one
project, TEN were taken on that sentence alone, and not one of them was this
distribution's. A plaintext password in the project's own ASP sources. Missing
alt text in a WordPress plugin that is its own git repository. A pip package
absent from a container image. A dev container that was not running. Two stale
backup archives. An inbox a maintainer reads as "defects in this distribution"
was 77% another tree's, and every row in it would have been re-filed on every
audit of that project.

`deferred.md`'s own BLOCKING rule already said the row names the repository's
path; the intake was not holding it. A row is now taken when its OWN text names a
shipped script, an install path, or the category in words. The script names are
read from the directory this file runs in — its siblings ARE the shipped scripts,
so the test cannot go stale when one is added.

THE SHIPPED-SCRIPT SIGNAL IS WHAT MAKES THE TIGHTENING SAFE, and it is measured
on the two projects that filed real rows: all 7 from `university` and all 3 real
ones here keep matching. `university`'s row 16 is the case that proves it —
`wf-catalog --migrate lists files for removal that it should not`, discharge cell
`Scan kept files as readers.`, no loose signal anywhere in the cell the matcher
reads, and kept because it names `wf-catalog`.

upstream-declared-only-not-taken is the negative and fails without this change;
upstream-report-real-shape is the positive that would break on an overreach.

Also here, from the code review of this batch: `capability_gap` fell to the
REMOVING side on an unreadable project file, because `slurp` returns "" for a
failed read and for an empty file alike, and no keys means no gap. A file nobody
can read is a file nobody can prove redundant — the same direction `wf-census`
takes for a copy it cannot read.

repository is written in. An upstream row is a defect measured in somebody
else's tree, so the one thing its evidence is guaranteed not to be is a file

A name match is not a capability match, and --kind did not scope --migrate

Two defects in one command, measured together on a live host 2026-10-02.

`--migrate` classed the project's `agents/character-scanner/AGENT.md` as
residue because the install ships an agent of that name. Only the project copy
emits the *Verification Preamble* that `text-eval/SKILL.md` and
`agents/tells-evaluator/AGENT.md` both require, and the install's copy does not
mention it once — so `--execute` would have left that requirement
unsatisfiable, which is the one thing the header promises a retirement never
does. `shipped_agents` answers "does the install ship a file of this name" and
`classify` was reading it as "does the install ship this capability"; those are
the same question only for a copy nobody edited.

A bundled agent is now compared SECTION BY SECTION against the shipped file of
the same name, and every section only the project's copy carries is printed
beside the STAYS. Lifting is not the alternative: the rows of a removed corpus
file are lifted into CATALOG-ANCHOR.md and the resolver reads them there, but
nothing spawns an agent out of an anchor, so a definition lifted as prose is
text about a capability that no longer exists. A bundled agent with no gap still
retires — `stale-twin` is that half, inside the same fixture.

`--kind` was accepted by `--migrate` and ignored. The flag already scopes
`--path` and `--grep`; migrate classified all five kinds and `--execute` acted
on all five, so a tree with one kind safe to retire and one that must not be
could only run both or neither. It now scopes both halves, hook registrations
included: a registration for a kind this run is not touching cannot be made
dangling by it.

catalog-migrate-kind-scopes is the proof of the second, and of why it mattered:
run against HEAD~1 with `--kind code --execute`, it deletes the text copy's
corpus AND its divergent agent.

A cross-scope agent pair is the install's own output, not a blocking collision

`wf-census` exited 2 on `character-scanner` registered in BOTH scopes with
differing bytes — a blocking precondition of the Atomic-or-Absent gate, so the
audit halted. Fourth instance of the class `collisions()` already records three
times (symlink aliases, in-skill templates, the byte-identical canary pair).

NEITHER SIDE IS THE RUN'S TO DELETE, which is what makes it the distribution's
defect. `manifest.txt` carries four `agent` rows, so `install` registers a
shipped evaluator's agent into the agents/ directory of the scope it installed
into, and a project keeping its own customized copy of that evaluator registers
the same name at project scope. `install` already states the rule for the other
scope — "REPORTED, NEVER REMOVED. The other scope is not this install's to
edit" — and `scopes.md` says everything an audit generates is written under
`${CLAUDE_PROJECT_DIR}/.claude/`. A gate whose only remedies lie outside the
tree the run governs cannot be cleared by the run.

MEASURED 2026-10-02 on a live host: one differing cross-scope pair, exit 2, and
the project copy is the one `text-eval/SKILL.md` requires — it emits the
Verification Preamble the install's copy does not mention. So the remedy the
gate implied was to delete a capability the project's own skill depends on.

SAME SCOPE IS UNTOUCHED AND STILL BLOCKING: two entries in one agents/ tree are
decided by filesystem read order with nothing documented either way, both are
the user's to rename, and the audit writes into exactly that directory. The
content split that distinguishes a DUPLICATE is unchanged and runs first; the
scope split runs after it and moves only the verdict.

No winner is asserted. Cross-scope precedence is NOT part of platform.md fact 5
and nothing here has measured it, so fact 5 now says so and the row names both
copies. `audit-setup.md` carries SHADOWED beside LIVE, DUPLICATE and NAMESPACE.

census-shadowed-cross-scope fails without this change; census-collision is the
same-scope half and keeps its exit 2.

wf-seed called a retired copy's success its own error, forever

A `text-eval` copy retired before `wf-catalog --migrate` learned to rewrite the
`additions-seeded` pin (1.71.0) still records `method=region
region-file=references/text-tells.md` — the file the retirement removed. No
candidate resolves, so `plan_catalog` reported `ERR … region target not found`,
`INV-SEED … 1 error`, exit 3, on every audit.

MEASURED 2026-10-02 on a live host, where `wf-catalog` reported 0 additions
unseeded for the same tree. Nothing could clear it: `--migrate` rewrites the pin
only for a kind it still has files to retire, and a copy whose corpus already
moved has none.

The pin is this script's own record that a region once had a home here. With
every candidate gone the copy carries no corpus file for the kind at all — the
end state a retirement is FOR — and the slot resolved one step earlier proves
the install carries the additions. So it reports `retired`, names the stale pin
and the paths it looked at, and exits 0.

REPORTED, NEVER REWRITTEN. wf-seed does not record `method=retired` itself: a
file deleted by accident is indistinguishable from one a retirement removed from
this side, and writing the wrong one of those would silently stop the additions
propagating forever. Restoring the file resumes seeding into it, and that is the
remedy the row names.

A never-seeded copy is still an error, which `seed-no-target` pins and keeps:
with no pin, nothing says a region ever lived there and the resolver may not
invent a target. `seed-stale-pin-corpus-gone` is the new case and it fails
without this change.

A run-directory reap has no SKILL.md, and the journal check demanded one

`wf-conform.check_journal` asked every path-shaped T7/T7s row for a
`staging/<name>/SKILL.md.orig`. `audit.md` § Step 5h reaps a run directory
through that same T-order — T7s stages, T7c marks, Step 6c unlinks — and
`.claude/workforce/work/<run-id>/` holds no `SKILL.md` to copy, so the staged
`tree/` is the whole of its undo.

MEASURED 2026-10-02 on a live host: 23 correctly staged `work-reap-*` rows
(seq 134–156, all T8-swept) failed `.orig exists on disk` while
`check_removal_set` passed for all 23 with the undo tree found on disk.
`verify` exited 1, so INV-VERIFY was NOT UPHELD and any later sweep refused.
The only ways to clear it were to invent an `.orig` for a directory that never
had one or to edit the journal — both falsify the record, which is what makes
this the checker's defect and not the project's.

The fix is per class, not per row. A target that is a skill by NEITHER reading
— its path cell is not under `.claude/skills/`, and its staged `tree/` holds no
`SKILL.md` — is answered by its whole-directory undo and its `prior-sha` is not
compared against a file. A skill journaled under an unconventional path cell
keeps the strict `.orig` + sha check, because the staged tree still says skill.
Step 6-S now defines the case rather than leaving it to the checker.

Both halves have a fixture, and both fail without this change:
conform-journal-reap-undo is the correct after-state and must pass;
conform-journal-reap-no-undo has no staged tree at all and must still fail,
naming the whole-directory undo rather than the `.orig` a run directory never
had.
