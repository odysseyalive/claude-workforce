Work list: a peer's checklist line names its sender, and says how an FYI closes

Feedback from oa-work (odyssey-alive de3efe49), measured on 1.82.0 once a
peer's message opened i8: the asks-checklist line never said who sent the
request, though the issue records `peer`. And a pure FYI from a peer opens
an issue too. That stays: a hook cannot tell an FYI from a request without
classifying free text. The session is told what to do with one instead.

Changes in wf-task-tag:
- PEER_LINE, said on a peer's message only, after the line's last
  sentence about the list: the message came from the peer session
  "<from-name>" (its `from` address when it has no name), not from the
  user, and a peer message that asks for nothing gets one item stating
  what it said, "status": "answered", and the issue closes. `answered`
  is already a finished status, so the issue closes by the existing path.
- peer_sender makes the name-or-address choice once, for this line and
  the index row's `from`. flat_sender is the flatten-and-cap peer_request
  already applied, now applied by both.
- A user message's line and the carry-only line are unchanged.

Fixtures: tasktag-peer-request-opens-an-issue-with-its-sender wants the
sender sentence and the clause. New:
tasktag-peer-request-without-a-name-is-shown-by-its-address, and
tasktag-user-message-line-names-no-peer, which forbids both on a user's
message. The two peer cases fail on 484e812. script-conformance 669/669,
conformance 17 fixtures 85 assertions, idempotence 14/14.
