A reversal you cannot run is not a reversal (v1.21.1)

The peer session reviewing v1.21.0 flagged that the user-scope write
reaches every session on this machine, said the record in
.settings-owned.json was the right shape, and left it alone.

The record was the right shape. Nothing could execute it.

`--wire-defaults` wrote hooks_added and output_style_previous and NO CODE
READ EITHER. hooks.md § Unwiring described an agent reading the sidecar
and hand-editing settings, which covers the hooks and never mentioned the
output style at all. So the one write that reaches every project on a
machine was the one with no runnable way back -- and it slipped through
because the artifact LOOKED like the remedy, which is how a detector with
no fix always slips through.

`--unwire-defaults` is the producer. Exactness is the whole contract: a
registration goes only when event, matcher AND command all match a
recorded row, so a hook the user wired themselves survives and an entry
holding other hooks beside ours keeps them. Verified against a tree
seeded with the user's own Stop hook and an Explanatory style -- both came
back untouched, and a second run is a reported NOOP.

A style that was absent before is DELETED rather than set to a default.
output_style_previous of None means the key did not exist, and writing one
back would be this project inventing a preference the user never had. A
style the user changed after we set it is reported and left alone.

The general rule now sits with the three paths in enforcement.md: a path
in needs a path out, and the way out needs a producer too. A mechanism
the installer and `audit` both wire is one the user never typed, so its
reversal cannot be a paragraph telling an agent to edit JSON by hand.

5 prove cases, all PROVEN, none vacuous.
