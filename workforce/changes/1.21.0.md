Three paths, or it does not propagate (v1.21.0)

v1.20.0 shipped the fix and one way to turn it on: a human typing a
command, once per machine and once per project. Francis runs this on
several servers. "I can't have manual commands being run ... no user will
want to do that."

A per-machine command is not a propagation path. It reaches exactly the
machines somebody typed it on, and everywhere else it is
indistinguishable from dormancy -- which is the state four inherited
hooks were deleted for, reached through the gesture instead of through
the file.

So the rule, in enforcement.md: a shipped mechanism needs all three of
the installer wiring it, `audit` wiring it again, and `verify` reporting
it absent. The second row is the one that gets skipped and the one that
matters most. A fix reaching only future installs leaves every org
already in the world where it was, on a tree that does not look broken.
That is the second half of the directive, and it is the harder half:
"needed changes like this need to be done in such a way that the next use
of workforce will heal the situation, even if it needs ran through an
audit again."

Found while building it: audit.md Step 6-G has read "this sits alongside
the settings-hook wiring of the same run" since the day it was written,
and NO STEP PERFORMED THAT WIRING. Same shape as the three v1.18.0
findings -- a rule written, a reader pointed at it, nothing that could
satisfy it. Step 6-H is the producer.

One producer for all three paths. `wf-settings-apply --wire-defaults`
registers every DEFAULT_HOOKS entry and selects the output style in one
call; both installers and Step 6-H call it. Two lists instead of one
producer drift inside a single release, and the drifting copy is the one
a user installs. OPT_IN_HOOKS stays out -- a heal step that quietly
widened the set would be a decision the user never made, arriving through
a command they ran for another reason.
