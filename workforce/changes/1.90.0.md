Handoffs carry across Claude accounts: a portable check, wf-account-sync, and the marker alone on its line

Requested through mutze-dev: "when we do a handoff that the work involved isn't
account-centric but could be reawoken effectively through a different user account
all-together". mutze-studio moved from ~/.claude to ~/.claude-brooke and lost memory,
skills, running work and page ownership on the way.

handoff/SKILL.md: JOB.md gains an account: line; ## Running items carry Output: and Re-run:;
a ## For another account section names the memory choice (synced or carried into the repo),
the install state, and each page's owner account and local source. Write can update an open
handoff in place. Everything a handoff needs lives in the job folder or the repo, never in
the scratchpad, a memory dir or a config-root skills path (from oa-work). Pick-up runs this
account's own sync, never a script the handoff names.

wf-account-sync (new): copies memory/ and the workforce install from one config dir to
another. Display by default, --execute to write. It backs up first and copies only where the
target is older. It refuses credential files, never follows links (O_NOFOLLOW sources,
O_EXCL temp files), and accepts --from and --to only as realpath'd dirs directly in $HOME
named .claude* (the user's choice). Ten fixture rows.

wf-task-tag: the agent-say guidance puts the re: marker alone on the first line, because
agent-say 1.2.56 copies it into the header only then (mutze-dev's reply failed to thread).
REPLY_POINTER gains a row.

install: prune deletes a recorded path only inside the root being installed

Rule 2 deleted every path in `.installed-external` that this run did not write,
wherever it pointed. ~/.claude-brooke was made by copying ~/.claude, so its record
listed 42 ~/.claude paths, and `update` under CLAUDE_CONFIG_DIR=~/.claude-brooke
pruned 12 sibling skills and 2 agent registrations out of ~/.claude.

A recorded path is now deleted only when its directory, resolved with `cd -P`
(symlinks and `..` followed), lies under this scope's skills, agents or
output-styles dir past a slash boundary. Any other row is never deleted, is
dropped from the record, and gets one "Not pruned <path>: outside ..." line.
The bundle guard and the empty-directory rmdir walk read the resolved path too.
install.ps1 gets the same check: Resolve-FullPath folds `..`, and a linked or
junction component under the root is refused. The ps1 change was not executed;
pwsh is not on this machine.

Fixture install-prune-stays-in-its-root runs the real installer offline through
fixtures/scripts/install-driver.py. It fails on 9d593ec.

build-as-you-go: a stock playbook for building one shareable page live, piece by piece

Requested through ps-dev: "a new stock playbook skill, 'build as you go' (live artifact
dialogue) ... Please call it a playbook, not a blueprint."

The method from that session, made stock: diagram first; one change per turn republished on
the same file_path with a version label; each reply opens with What changed; the newest
instruction replaces the old; the page grows overview -> zoom -> sections in build order ->
subsections -> stubs -> two-way links -> Q&A. Confirmation is the walk-through; a chooser
only for the principal's irreversible calls, such as sharing. Research goes to read-only
background agents from a 5-line brief. Before each publish, a playwright-mcp checklist runs
against a localhost server. Privacy: private by default, with a forbidden-terms grep and a
terms file kept outside the served folder. Style defers to shared-artifact.

handoff: a stock skill to write a handoff and pick up from the newest one

The user, through tr-dev: "please add a handoff skill as a stock feature ... the user just
has to ask for a handoff whenever they feel the need." A fresh tr-dev session asked to pick
up from the latest handoff found none and had to dig the state out of a transcript.

A handoff is a working-files job folder, .claude/workforce/jobs/handoff-<stamp>/JOB.md,
with the four job lines plus handoff: open, branch and head, and fixed sections: Committed,
Uncommitted, Running, Open items, Waiting on the user. Pick-up checks each claim against git,
reports what changed, marks it consumed and continues from next:. wf-heal's session start
names the newest open handoff on a HANDOFF line, even past the listing cap, and keeps it out
of the delete offer. One mechanism, not a second store; the retired wf-handoff stays retired.

Peer replies carry the marker they answer, and a spawn's items reach it after its meta file lands

Two peers answered a marker with their own session/issue (tr-dev answered b59b3de3/i3 with
26dc3176/i5), so every reply opened a fresh issue on the other side. Rule now, stated in the
guidance: a new thread carries the sender's own marker; a reply carries the marker the
message it answers arrived with. A foreign marker is recorded on the issue per sender
(reply_markers), that turn's guidance names it for the reply, and a later message carrying
it continues that issue.

Live, the SubagentStart hook finished 0.26 s before the harness wrote the agent's meta file,
so the spawn fell back to the newest issue with no items. relink_agent now runs once from the
agent's own PostToolUse (wf-turn-budget, after the cap check) and records the issue and
items its order names. bin/script-conformance gains a step that writes a file between events,
so a fixture can reproduce that timing.

Work list across sessions: spawns link to the issue their order names, labels go per item, and peer replies continue their issue

Reported by oa-work from odyssey-alive's ledger, where i5 listed agents that served i4,
4e381c9f's "/agenda today" stayed open a month with nothing open, and every pw-dev reply
opened a new issue instead of continuing i7.

- A spawn is linked by an `Issue: iN [items 2, 3]` line in its prompt; the working label
  goes only on the items it names. The fallbacks are the description, then the newest issue.
- When the work list is shown mid-turn, its items and title are written to the ledger and index.json (sync_list).
- An exited session's issue with no open items and no live agent closes at the next read
  (close_dead); a handoff mark older than 30 minutes counts as over.
- A `re=<s8>/iN` header marker or leading `re: <s8>/iN` body line continues that issue,
  or links to another session's issue; guidance tells sessions to write it.
- An ask of 12+ words matching an open ask in another session shows `see <s8> iN`; not merged.

The finding-without-an-item nudge is not shipped: at least 4 of its 16 fires on 2,996 real Stops were wrong.

The work list shows earlier sessions' open issues, and a running agent's issue says who is on it

Every /clear or restart starts a new session, and the list read only that session's ledger, so
tmux-revive's index listed 7 open issues across 4 earlier sessions that the current session
never showed. After this session's own lists, the display adds OPEN FROM EARLIER SESSIONS,
built from index.json and the ledger files it names, capped at 10 items with a count of the
rest. Those items ride in "carried" with a "session" key, because issue ids repeat across
sessions. A mark on one lands in that session's ledger, closes the issue there and drops it
from index.json. Sessions the registry shows running are never shown or written. Rows whose
issue has a running agent say "working (<type>)" and sort first, so new messages cannot push
them past the caps.
