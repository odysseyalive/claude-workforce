Release 1.79.1: update and verify say whether THIS project needs an audit

User, 2026-10-16: "when the workforce update is done, it requests the user to
audit their project again. I thought on the last several updates you mentioned
that there was no need for an audit." ... "if there is a necessary need for an
audit. I'm good." ... "but something might have changed."

Two causes, both fixed:

- bin/gen-changes flagged a release "Org: yes" whenever a copied template file
  changed at all. 1.9.0, 1.50.0, 1.72.0 and 1.78.0 changed only the maintainer
  coverage comment on line 3, which no org copies, and each told every user to
  re-audit. `comment_only_change` now skips a change made only of whole-line
  HTML comments outside fences that are not region markers; a fenced line, a
  marker, prose, or a created/deleted file still flags.

- update step 7 decided "audit or not" from those release flags plus whether
  .claude/agents existed, so every project got the same answer. New
  workforce/bin/wf-due measures it per project: the oldest workforce-version
  stamp among authored handbooks (the chart's only as a fallback) against the
  change index, plus each Core skill's state. It prints NO AUDIT NEEDED,
  AUDIT NEEDED with each reason, or COULD NOT TELL, and update step 7 and
  verify's Output both close with its line, so the two can't disagree.
  Handbook stamps, not the chart's: on odyssey-alive an audit today stamped 21
  handbooks 1.79.0 while the chart still said 1.76.0, and org index restamps
  the chart on every hire without healing a handbook.

Demonstrated: classifier cases (comment edits skip; fenced, marker, prose and
new-file changes flag); wf-due on seven real projects and on planted trees
(old handbook under a new chart, unreadable Core skill, missing root);
wf-due runs from a bin/dev-sandbox install, which was removed. An independent
review found four defects in wf-due's first cut (two false "no audit"), all
fixed and re-run here.
