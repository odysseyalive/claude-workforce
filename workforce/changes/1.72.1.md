--resolve could not take the id --list prints, and a bare row id closed every project's row 1

MEASURED on this machine's real inbox, seven rows filed from `university`. `--list`
prints `university--1.md` and its own hint says `--resolve <id>`, and neither
`--resolve university--1.md` nor `--resolve university--1` matched anything. The matcher
asked whether the file stem ENDED WITH the separator followed by the whole id, which
`university--1` never does — it would have to read `university--university--1`.

**So the only form that worked was a bare `1`, and that is the part that matters.**
Every project's deferred queue numbers its rows from 1, so a bare `1` matched row 1 of
EVERY project in the inbox and closed all of them — silently, on behalf of an operator
looking at one. Reproduced: against the old matcher, `--resolve 1 --execute` stamps
`version=1.72.1` into both `university--1.md` and `odyssey-alive--1.md`. A convenience
that quietly edits a queue nobody was looking at is worse than no convenience.

THREE SPELLINGS, AND THE LAST ONE IS GUARDED, in `resolve_targets`:

    university--1.md   the id --list prints, extension included
    university--1      the same id without it
    97                 a bare row, ONLY where it is unique across the whole inbox
    1                  REFUSED, with every candidate named

The bare form is kept rather than banned: a rule rejecting every bare id would be safe
and useless, and the operator would stop using the convenience instead of its ambiguous
half. Where it is ambiguous the refusal lists the candidates and says the full form
always resolves, so the next gesture is a paste rather than a guess.

THE STEM IS COMPARED WHOLE, never split on `--`. A scrubbed row id can itself contain
`--` — `x-------wf-upstream-v1` is a real one, from a row id carrying a comment
terminator — so splitting on the separator is guesswork and comparing the whole stem is
not.

The per-file `Closing it` hint printed the BARE row, which walked the reader straight
into the refusal. It now prints `<project>--<row>`.

Four fixtures over one pre-seeded inbox holding two projects that share row `1`: the
full id, the stem, a unique bare row, and the collision. Three fail against HEAD; the
collision case fails there by exiting 0 and stamping the version into BOTH projects'
files, which is the defect itself. `upstream-resolve-unique-bare` passes before and
after, and is in the set because the guard must not swallow the legitimate case.

The `bin/check` assertion carries a NEGATIVE conjunct — the broken clause must be GONE —
and that is load-bearing: a file adding the new matcher while leaving the old clause in
place satisfies every positive and still closes another project's row. The old
expression is DESCRIBED rather than quoted in the docstring for the same reason; a copy
of it in prose would satisfy the grep and make the assertion pass over the defect.

`bin/prove "upstream: --resolve"` → 1 of 1 proven by breaking.

A release bump is not a behaviour change — the corpus masks the checkout's own version

MEASURED on the 1.72.0 release: `wf-conform` prints the installed version, so the
golden said `installed 1.71.1` and the run said `installed 1.72.0`. `bin/check` failed
the corpus on a real org with no code change — **and a version bump is the exact moment
this suite runs**, which makes it the worst possible false fire: green all the way
through development, red on the release.

Same class as the `CLAUDE_EFFORT` leak one commit earlier: a value belonging to the
environment of the run rather than to the tree under test. `normalise` now masks the
checkout's own `WORKFORCE-VERSION` to `<WF-VERSION>`, read from `version.md` at run
time so a worktree at any version normalises to the same text.

A VERSION A PROJECT STAMPED IS REAL DATA AND STAYS. `stamped 1.70.0` is what that
handbook was authored against; it does not move when this checkout bumps, and masking
it would stop the golden tracking it. Only the checkout's CURRENT number is replaced,
so the two are distinguished by value — which is what they are. The single collision is
a project whose stamp equals the version under development: that stamp is masked too,
costing precision in the one case where the numbers are genuinely indistinguishable,
and never producing a false fire.

THE BOUNDARIES WERE THE FIDDLY PART, and the worktree test is what caught them. The
first spelling used `(?![\w.])`, which refuses a version followed by ANY period — so
`installed 1.72.0` in the summary line was masked and `the installed release is
1.72.0.`, the same fact ending a sentence, was not. The lookahead now blocks a word
character, and a period only when a digit follows, which is what stops `1.7` rewriting
the front of `1.72.0` while a sentence-ending period passes. The lookbehind blocks a
digit or a dot rather than any word character, so a `v`-prefixed form is masked and
`11.72.0` is not. Eight boundary cases checked by hand.

THE CHECK BUMPS THE VERSION, it does not read the regex. `corpus: a release bump is not
a behaviour change` copies this checkout into a throwaway directory, sets
`WORKFORCE-VERSION: 9.99.0`, and runs the corpus against the real goldens expecting no
diff. Asserting on the masking pattern would have asserted on my own spelling of it,
and my own spelling was wrong — only a run at a different version showed it. `corpus/`
is symlinked rather than copied: it is 18 MB, every golden exists, and nothing is passed
`--accept`, so the run writes none of them.

University's goldens were re-recorded once. Verified: no `1.72.0` remains in any golden,
every `stamped 1.70.0` does, and a scratch copy at `9.99.0` reports
`26 case(s) compared · 0 FAILED`.
